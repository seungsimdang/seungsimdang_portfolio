# T02 요구사항 정의서 - 프로젝트 썸네일 확장

- 작업 브랜치: `feature/project-thumbnails`
- 입력: `artifacts/task-team/00-input.md`
- 상태: 사용자 확인 게이트 통과 (2026-10-16). 확정 내용은 11절이 8·9절 제안보다 우선함.

## 1. 목적

프로젝트 카드 썸네일을 (1) PC 뷰와 모바일 뷰에서 다른 이미지로, (2) 프로젝트당 여러 장으로 지정할 수 있게 하고, 여러 장이면 일정 시간마다 자동 전환한다. 구분이 없는 기존 프로젝트는 화면이 픽셀 단위로 그대로 유지된다. 구현 후 SEMT 프로젝트 데이터를 지정 이미지로 갱신한다.

## 2. 현재 상태 (코드 확인)

- `projects.thumbnail`은 단일 nullable `text` (`src/db/schema/portfolio.ts`).
- 서버 검증 `isValidThumbnail`은 `NEXT_PUBLIC_BLOB_HOSTNAME`의 `/thumbnails/` 경로 Blob URL만 허용 (`src/schemas/portfolio.schema.ts`). Globber의 `public/images/projects/globber/thumbnail.png`는 이 규칙 밖의 레거시 값이라, 수정 화면에서 바꾸지 않으면 형식을 따지지 않는 `projectFormKeepThumbnailSchema` 경로로 통과함.
- 도메인 타입 `Project.thumbnail?: string` (`src/types/portfolio.ts`).
- 사용처: `ProjectCard`(홈 `src/app/(public)/page.tsx`, `/projects` 페이지), 상세 `work/[id]/page.tsx`의 OG `images`, admin `project-form.tsx` + `thumbnail-field.tsx`, 업로드 API `/api/admin/uploads/thumbnail`(4MB 이하 PNG/JPG/WebP, Blob `thumbnails/`).
- `ProjectCard`: `next/image` fill + `object-cover`, 하단 그라디언트 오버레이, 카드 높이 `h-card`/`md:h-card-stuck`(projects 페이지는 `lg:h-card-tall`). `candanta` slug만 `preserveThumbnailText`(상단 정렬, 정사각 영역) 특례.
- 썸네일이 없는 프로젝트는 테마 배경색 + 테마 글자색으로 렌더, 있으면 흰 글자.

## 4. 수용 기준 (검증 가능한 형태)

### 4.1 회귀 보호 (최우선 제약)

- AC-R1: 썸네일이 없는 프로젝트의 홈·projects 카드는 변경 전과 DOM 구조·클래스·계산 스타일이 동일하다 (배경색, 글자색, 높이, 패딩).
- AC-R2: 구분 없는 단일 썸네일을 가진 기존 프로젝트(Globber, Candanta 등)의 카드는 모든 브레이크포인트(375, 768, 1024, 1440 이상)에서 변경 전 스크린샷과 픽셀 단위로 동일하다. 크롭 위치, 그라디언트 오버레이, 호버 확대, 포커스 링 포함.
- AC-R3: `candanta`의 `preserveThumbnailText` 동작(상단 정렬, `min(100%, 100cqh)` 폭)이 그대로 유지된다.
- AC-R4: 단일 썸네일 프로젝트에는 자동 전환 타이머, 인디케이터 등 어떤 추가 UI·동작도 생기지 않는다.
- AC-R5: 기존 프로젝트 데이터는 마이그레이션 후에도 같은 이미지가 같은 위치에 표시되며, 기존 값 손실이 없다.
- AC-R6: 단일 썸네일 카드의 `eager`/`lazy` 로딩과 `sizes` 동작이 유지된다 (첫 카드만 eager).

### 4.2 PC/모바일 분기 (F3, F5)

- AC-1: 기준 브레이크포인트(A1) 미만 뷰포트에서는 모바일 목록, 이상에서는 PC 목록 이미지가 표시된다.
- AC-2: 모바일 목록이 비어 있으면 모바일 뷰도 PC(기본) 목록을 표시한다. 둘 다 같은 이미지·같은 전환 규칙이다.
- AC-3: 뷰포트 리사이즈 시 새로고침 없이 맞는 목록으로 바뀐다.
- AC-4: 서버 렌더 HTML과 첫 클라이언트 렌더가 불일치(hydration mismatch)하지 않으며, 잘못된 쪽 이미지가 잠깐 보이는 깜빡임이 없다.
- AC-5: 현재 뷰에서 쓰지 않는 쪽 이미지는 불필요하게 로드하지 않는다 (네트워크 탭 확인). 단 구현 방식에 따라 가능한 범위에서 최소화하며, 불가 시 사유를 보고한다.

### 4.3 자동 전환 (F4, F10)

- AC-6: 현재 뷰의 이미지가 2장 이상일 때만 자동 전환한다. 간격과 효과는 A2 결정을 따른다.
- AC-7: 마지막 이미지 다음에는 첫 이미지로 순환한다.
- AC-8: `prefers-reduced-motion: reduce`에서는 A2 결정에 따라 자동 전환을 하지 않거나 효과를 제거한다.
- AC-9: 호버·포커스 중 일시정지 여부는 A2 결정을 따르며, 기존 호버 확대(`hover:scale-[1.02]`)와 충돌하지 않는다.
- AC-10: 탭이 비활성(visibility hidden)일 때 전환이 누적되어 복귀 시 연속 점프하지 않는다.
- AC-11: 뷰 전환(PC↔모바일) 시 전환 인덱스가 0으로 초기화되고 타이머가 중복 생성되지 않는다. 언마운트 시 타이머가 해제된다.
- AC-12: 전환 이미지가 스크린리더에 중복 낭독되지 않는다 (현재 표시 이미지만 alt 노출). 이미지 alt는 `{title} 프로젝트 썸네일` 형식을 유지한다.
- AC-13: 홈에 카드가 여러 개여도 각 카드의 전환은 독립이며 성능 저하가 없다 (불필요한 전체 리렌더 없음).

### 4.4 이미지 맞춤 (A3)

- AC-14: 모바일(세로형 9:19.5) 이미지가 카드(가로로 넓음, 고정 높이) 안에서 A3 결정대로 표시되며, 제목·역할·기간 텍스트와 그라디언트 오버레이 가독성이 유지된다.
- AC-15: 카드 높이는 이미지 비율에 따라 변하지 않는다 (레이아웃 시프트 없음, `h-card` 계열 유지).

### 4.5 데이터와 admin (F1, F2, F6, F7)

- AC-16: DB는 프로젝트당 PC(기본) 목록과 모바일 목록을 순서 있는 배열로 저장한다. 저장 순서가 전환 순서다. (스키마 형태는 A4 결정, 구현 방식은 개발자 영역)
- AC-17: admin 폼에서 각 목록에 이미지를 추가, 삭제, 순서 변경할 수 있고 저장 후 공개 화면에 반영된다. 기존 업로드 규칙(PNG/JPG/WebP, 4MB 이하, Blob `thumbnails/`)을 재사용한다.
- AC-18: 한 목록의 최대 개수 상한을 서버 스키마에서 강제한다 (제안: 목록당 10장). 초과 시 필드 오류를 반환한다.
- AC-19: URL 허용 규칙은 기존과 동일하다 (등록된 Blob 스토어 `/thumbnails/` 경로만). 기존 레거시 값(Globber 정적 경로)은 바꾸지 않으면 저장 시 거부되지 않는다.
- AC-20: 중복 URL, 빈 문자열 항목은 저장 전에 제거되거나 필드 오류로 안내된다.
- AC-21: 수정 화면에서 썸네일을 건드리지 않고 저장하면 기존 썸네일 값이 변하지 않는다 (현재 `savedThumbnail` 비교 동작과 동등).
- AC-22: 업로드 진행 중에는 저장이 막힌다 (현재 동작 유지). 여러 장 동시 업로드 시에도 마찬가지다.
- AC-23: 프로젝트 삭제·slug 변경·정렬 변경 같은 기존 admin 동작이 회귀하지 않는다.
- AC-24: 저장에서 제거된 이미지의 Blob 파일 정리 여부는 기존 동작과 동일 수준을 유지한다 (확인 필요 E2).

### 4.6 OG 이미지 (F8)

- AC-25: A6 결정에 따라 상세 페이지 OG `images`가 설정된다. 썸네일이 없으면 현재처럼 `images`를 생략한다. 단일 썸네일 프로젝트의 OG 값은 변경 전과 동일하다.

### 4.7 SEMT 데이터 (F9)

- AC-26: 구현·리뷰·QA 통과 후, 사용자 승인을 받은 뒤에만 운영 DB와 스토리지를 변경한다.
- AC-27: SEMT PC 목록은 `SEMT 썸네일 1920×1080@1x.png` 1장(D6), 모바일 목록은 03-03, 02-02, 04-04-Know-each-hospital 순서 3장이다.
- AC-28: 반영 후 PC 뷰는 1장 고정(전환 없음), 모바일 뷰는 3장 자동 전환임을 실제 화면에서 확인한다.
- AC-29: SEMT 외 프로젝트 데이터는 변경되지 않는다.

## 5. Edge case

- E-a: PC만 있고 모바일 없음: 양쪽 PC 목록 (AC-2).
- E-b: 모바일만 있고 PC(기본) 없음: A4 권장안에서는 PC 뷰에 썸네일이 없는 상태가 됨. 저장 시 거부하거나 경고할지 결정 필요 (A4 부속 질문).
- E-c: 목록에 1장: 전환 없음, 인디케이터 없음.
- E-d: 이미지 로드 실패(404 등): 해당 이미지는 건너뛰거나 배경색 폴백. 카드 레이아웃이 깨지지 않아야 함.
- E-e: 이미지 비율이 장마다 다름: 카드 고정 높이 + 동일 맞춤 규칙으로 크기 변동 없음.
- E-f: 전환 중 호버 확대, 키보드 포커스 동시 발생.
- E-g: SSR/정적 생성(`generateStaticParams`) 시 viewport를 알 수 없음. 서버에서 한쪽만 고르면 불일치 발생 (AC-4).
- E-h: 느린 네트워크에서 다음 이미지 미로드 상태로 전환되면 빈 화면이 보이지 않아야 함 (선로딩 또는 이전 이미지 유지).
- E-i: 같은 URL이 PC/모바일 목록에 중복.
- E-j: `candanta`의 `preserveThumbnailText` 특례와 복수 장/모바일 목록의 조합 (특례 대상은 현재 단일 장이므로 범위 외로 두되 회귀 금지).
- E-k: 서로 다른 프로젝트 간 URL 공유 여부 (Blob 정리 시 영향).

## 6. 비기능 요구사항

- 성능: 모바일에서 PC용 3840px 이미지를 받지 않는다. `next/image` 최적화 경로를 그대로 사용한다. LCP 첫 카드는 eager 유지.
- 접근성: 5.3 AC-8, AC-9, AC-12. 자동 전환에 대한 WCAG 2.2.2(Pause, Stop, Hide)를 고려해 일시정지 수단 필요 여부는 A2에서 결정.
- 보안: 새 URL 필드도 기존과 같은 Blob 호스트·경로 allowlist 검증. 클라이언트 입력을 신뢰하지 않고 서버에서 검증. admin API는 기존 `adminRoute`/인증을 따른다.
- 코드 규칙(제약): `docs/agent-rules/` 준수. 파일명 kebab-case, Tailwind spacing은 px 환산, 디자인 토큰 사용, 주석 규칙(명사형 종결, em-dash 금지), `knip` 미사용 코드 금지, 테스트 제목 한글.
- 동시성/유일성: 새 중복 생성 기능 없음. 단 admin 저장은 기존 PUT 덮어쓰기 모델을 따른다.
- 배포/크론: 신규 크론 없음. 배포 경로는 기존 Vercel 흐름. 마이그레이션은 `drizzle/`에 추가되며 운영 적용은 사용자 승인 후. 신규 환경변수 없음 (기존 `NEXT_PUBLIC_BLOB_HOSTNAME`, Blob 토큰 사용).
- 컴포넌트 props 전달: `ProjectCard`는 현재 `thumbnail?: string`만 받음. 새 값(PC 목록, 모바일 목록)은 홈(`(public)/page.tsx`)과 `/projects` 페이지 두 호출부 모두 `project`에서 전달해야 하며, 한쪽만 바꿔 누락되지 않게 한다.
- 목록 일부 표시 메시지(4-4): 해당 없음 (카드는 현재 이미지 1장만 보이고 총 장수 텍스트 UI는 요청되지 않음). 인디케이터를 넣을지는 A2의 부속 항목.
- 능동 트리거(4-5): 자동 전환은 사용자 방문 중 클라이언트 타이머가 트리거 주체이며 크론 불필요.

## 7. 범위 외

- 프로젝트 상세 페이지에 썸네일 갤러리 추가.
- 호버 확대 등 기존 카드 인터랙션 변경.
- 썸네일 외 이미지(블로그 등) 처리 변경.
- 사용자가 요청하지 않은 인디케이터·수동 이전/다음 컨트롤 (A2 결정에서 사용자가 추가하면 포함).

## 8. 사용자 확인 필요 항목 A1~A7 (모두 제안)

### A1. PC/모바일 기준 브레이크포인트

- 제안: `md`(768px) 미만을 모바일, 이상을 PC로 본다.
- 이유: 카드 높이가 이미 `h-card` → `md:h-card-stuck`으로 `md`에서 바뀌고, 패딩·글자 크기도 `md`에서 바뀐다. 카드 시각 단위와 이미지 분기를 일치시키는 것이 일관적이다. 768~1023 구간은 카드가 전체 폭으로 넓어 가로 이미지가 더 맞다.
- 대안: `lg`(1024px). 태블릿 세로(768~1023)에서도 모바일 이미지를 쓰게 되나, 이 구간 카드는 폭이 넓어 세로 이미지 크롭이 심해진다.

### A2. 자동 전환 간격·효과·일시정지·reduced-motion

- 제안: 간격 4초, 효과는 크로스페이드(0.6초 내외), 호버·키보드 포커스 중 일시정지, `prefers-reduced-motion: reduce`에서는 자동 전환 중지(첫 장 고정). 인디케이터·수동 컨트롤은 추가하지 않음.
- 이유: 포트폴리오 카드는 스크롤 중 지나가는 요소라 짧은 간격이 적절하고, 페이드는 카드 호버 확대와 간섭이 적다. 호버 일시정지와 reduced-motion 중지는 WCAG 2.2.2 및 기존 `motion-reduce` 처리 방향과 맞다. 사용자가 요청하지 않은 UI는 넣지 않는다.
- 대안: 슬라이드 효과 / 간격 3초 또는 5초 / 일시정지 없이 전환 지속 / reduced-motion에서도 효과만 제거하고 전환은 유지 / 점 인디케이터 추가.

### A3. 세로형 모바일 이미지의 카드 맞춤

- 제안: 기존과 같은 `object-cover` 크롭 + `object-position` 상단 기준(또는 중앙)으로 채운다. 확정 위치는 SEMT 이미지 3장으로 디자인 단계(T03)에서 시안 확인.
- 이유: 카드는 이미지가 전체를 채우는 구조(그라디언트 + 하단 텍스트)이고 기존 렌더 방식을 바꾸지 않아 AC-R2를 지키기 쉽다. 모바일 뷰에서는 카드 폭이 좁아 세로 이미지 비율과 가까워 크롭이 적다 (`<md` 카드는 `h-card` 고정 높이).
- 대안: `object-contain` + 배경색 레터박스(이미지 전체 보임, 빈 영역 발생), 모바일 이미지를 카드 안에 폰 프레임처럼 중앙 배치.

### A4. 데이터 모델

- 제안: "기본 썸네일 목록 + 모바일 전용 목록(비면 기본 목록 사용)". 기존 단일 `thumbnail` 값은 기본 목록의 첫 항목으로 이전해 무손실 호환한다.
- 이유: 사용자 요구("구분 없으면 양쪽 동일")와 정확히 대응한다. 기존 프로젝트는 데이터 변경 없이 동작하고, 대부분의 프로젝트(구분 없음)는 한 목록만 관리하면 된다. 이후 PC 이미지를 바꿀 때 모바일 중복 수정이 없다.
- 대안: PC 목록·모바일 목록을 각각 독립 지정 (명시적이지만 구분 없는 프로젝트도 두 번 입력 필요, 한쪽 누락 시 처리 규칙이 별도로 필요).
- 부속 질문: 모바일만 있고 기본 목록이 비어 있을 때 저장을 거부할지 허용할지. 제안은 거부(PC 뷰에 이미지가 사라지는 것을 방지).

### A5. SEMT 이미지 저장 위치와 크기

- 제안: Vercel Blob(`thumbnails/`)에 업로드한다. PC 이미지(3840x2160, 2.07MB)와 모바일 3장(약 1.1MB)은 모두 기존 4MB 업로드 한도 안이라 원본 그대로 올린다. 표시 크기 축소는 `next/image` 최적화에 맡긴다.
- 이유: 서버 검증(`isValidThumbnail`)이 Blob `/thumbnails/` URL만 허용하므로 정적 파일 경로를 쓰면 admin에서 저장이 거부된다. Blob이면 admin 업로드와 같은 경로라 운영 데이터가 일관된다.
- 대안: `public/images/projects/semt/` 정적 파일 (Globber와 같은 방식이나 검증 규칙을 완화하거나 레거시 우회가 필요, 저장소 용량 증가). 사전 리사이즈(저장 용량 절감, 별도 작업 필요).
- 참고: 로컬 파일(`~/Downloads`, `~/Desktop`)을 업로드하는 작업과 운영 DB 변경은 사용자 승인 후 수행. 어느 환경(운영 직접 vs admin 화면 사용)으로 반영할지도 이때 결정.

### A6. OG 이미지

- 제안: 기본(PC) 목록의 첫 번째 이미지를 OG 이미지로 사용한다. 기본 목록이 비면 `images`를 생략한다.
- 이유: OG 카드는 가로형 미리보기가 일반적이라 PC 이미지가 적합하다. 단일 썸네일 프로젝트는 현재와 동일한 값이 나와 회귀가 없다. 목록 전체를 넣으면 플랫폼별로 첫 장만 쓰거나 동작이 불일치한다.
- 대안: 모바일 첫 장, 목록 전체를 `images` 배열로 제공.

### A7. admin 폼에서 복수 썸네일 편집

- 제안: 필요하다. 기본 목록과 모바일 목록 각각에서 추가·삭제·순서 변경(위/아래 이동)을 지원하고, 기존 `ThumbnailField`의 업로드 규칙을 재사용한다. 드래그 정렬은 범위 외.
- 이유: 편집 수단이 없으면 SEMT 및 이후 프로젝트 반영이 DB 직접 수정에 의존하게 되어 요구(복수 지정 가능)를 운영에서 지속 가능하게 충족하지 못한다. 순서가 곧 전환 순서라 순서 변경이 필요하다.
- 대안: 이번 범위에서는 DB/스크립트로만 입력하고 admin은 읽기 전용 표시 또는 기본 목록 단일 편집만 유지 (구현은 작지만 운영 편의성 저하, 회귀 위험은 낮음).
