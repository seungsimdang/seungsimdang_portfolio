## 2. 모호 항목 확정과 근거

근거는 이 저장소 코드와 이 Task에서 확인한 출처만 쓴다.

### 2.1 9번 토스트 적용 범위

결정: admin 콘솔 전체의 "작업 결과 알림"을 하나의 토스트 방식으로 통일한다.

| 대상 | 현재 | 결정 |
| --- | --- | --- |
| profile·project·talk·resume·blog 폼 저장 성공/실패/검증 요약 | `useAdminForm`의 notice, `FormStatus`(상단) 또는 `FormActionBar`(하단) | 토스트 |
| blog 폼 이미지 업로드 결과, .md 가져오기 결과, 삭제 실패 | `localNotice` -> `FormActionBar` | 토스트 |
| 목록 순서 저장 성공, 삭제 완료, 순서 저장/삭제 오류 | `SortableList` 내부 `message`/`error` 영역 | 토스트 |
| 목록 화면 "삭제했습니다." (`?deleted=1`, 프로젝트·발표·이력·블로그) | 화면 상단 `role="status"` 문단 또는 `initialMessage` | 토스트 |
| 편집 화면 도착 시 "저장했습니다..." (`?saved=1`, `initialSaved`) | 폼 notice 초기값 | 토스트 |
| 필드별 오류(`TextField`의 `error`, 썸네일 필드 오류) | 입력란 아래 | 유지(사용자 확정) |
| 진행 중 표시(저장 중 버튼 문구, "이미지 업로드 중...", "썸네일 업로드 중...") | 버튼/상태 문구 | 유지(결과가 아니라 진행 상태) |
| `SortableList`의 이동 안내 "n번째로 이동했습니다."와 "순서가 변경되었습니다. 저장해야 반영됩니다." | `aria-live` 문단, 상태 배너 | 유지(키 입력마다 나오는 스크린리더 안내와 미저장 상태 표시이며 작업 결과가 아님) |

근거:

1. 일관성. 현재 admin은 결과 위치가 폼마다 다르다(상단 `FormStatus`, 하단 `FormActionBar`, `SortableList` 자체 영역, 목록 상단 문단). 블로그 폼만 토스트로 바꾸면 같은 admin 안에 결과 표시 방식이 둘로 갈라진다. 요청 9는 "toast와 같은 방식이어야 하지 않을까"라는 방식 통일 질문이고, 요청 10도 "프로젝트 내 유사 로직 파악 후 모두 통일"이라 같은 방향이다.
2. 코드 사실. 5개 폼이 모두 `useAdminForm` 하나를 공유하므로(`use-admin-form.ts`) 알림 출력 경로를 한 곳에서 바꾸면 전체가 바뀐다. 블로그만 분기하려면 오히려 예외 코드가 늘어난다.
3. `FormStatus`와 `FormActionBar`의 요약 문구("저장됨", "저장 실패 (상세는 위 알림 참고)")는 토스트 도입 후 같은 정보를 이중으로 보여 주므로 제거한다. `FormActionBar`에서는 `notice`, `detailed` props를 제거하고 `busyMessage`(진행 상태)만 유지한다. `FormStatus` 컴포넌트는 사용처가 없어지므로 삭제한다(knip이 미사용 export를 막는다).
4. 범위 밖: `/admin/login` 화면(콘솔 셸 밖)의 오류 표시는 바꾸지 않는다.

오류 토스트 유지 규칙(사용자 확정을 구체화):

- 성공: `role="status"`, 자동 소멸. 닫기 버튼도 제공한다.
- 오류: `role="alert"`. 행동 링크(`다시 로그인`, `목록으로`)나 버튼(`logout`, `새로고침`)이 붙은 오류는 사용자가 닫을 때까지 유지한다(사용자 확정).
- 행동이 없는 일반 오류(예: "저장하지 못했습니다. 잠시 후 다시 시도하세요.", "N개 항목을 확인하세요.", 업로드 실패)도 자동 소멸시키지 않고 닫기 전까지 유지하며, 같은 폼의 다음 저장 시도나 성공 토스트가 뜰 때 이전 오류 토스트는 치운다. 이 줄은 사용자 확정에 없던 세부 결정이다. 근거는 아래 접근성 항목이며 7절에 확인 항목으로 둔다.
- 접근성 근거: W3C Understanding SC 2.2.1은 이메일 클라이언트의 5초 후 사라지는 토스트를 "사용자가 받은편지함 등 다른 수단으로 같은 정보를 알 수 있는 경우"의 예로 들며 시간 제한 예외를 인정한다. 같은 문서의 WCAG 2.1판은 다른 수단이 없으면 시간 조절 기준을 충족해야 한다고 적는다(https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html). 저장 실패 오류는 다시 확인할 다른 수단이 없으므로 자동 소멸 대상에서 제외한다. 성공 토스트는 폼의 저장 상태(저장 버튼 상태, 이탈 경고 해제)로 어느 정도 대체 확인이 되지만 이것이 충분한지는 해석의 영역이며 출처가 단정하지 않는다. 그래서 성공 토스트에도 닫기 버튼과 포인터 올림/키보드 포커스 중 소멸 일시정지를 둔다(자동 소멸 시간은 designer가 정하고 근거를 적는다).

### 2.2 4번 영어화 범위

결정:

| 대상 | 현재 | 변경 |

| 탭 진입(목록) 화면 `AdminPageHeader title` | 프로젝트, 발표, 블로그, 이력, 프로필 | 탭 이름과 동일 |
| 탭 진입 화면 `metadata.title` | "블로그 - admin" 등 | "blog - admin" 등 (화면 제목과 브라우저 탭 제목이 어긋나지 않게) |
| 본문 안에서 탭 이름을 가리키는 문구 | 이력 화면의 "프로필에서 편집합니다" 링크 텍스트 | 링크 텍스트를 탭 이름 `profile`로 맞춤 |
| 하위 화면 제목(새 프로젝트, 프로젝트 편집, 새 발표, 발표 편집, 새 글, 글 편집, 새 이력, 이력 편집)과 그 metadata | 한글 | 변경하지 않음 |
| 버튼·안내·오류 문구·폼 라벨·aria-label | 한글 | 변경하지 않음 |

근거:

- 소문자 관례는 공개 사이트 코드에서 확인했다. 공개 `Navbar`의 라벨이 `home`, `projects`, `about`, `blog`, `talks`, `contact`이고(`navbar.tsx`), 공개 `/blog`의 `PageHeader title="blog"`와 `metadata.title: "blog"`가 소문자다(`blog/page.tsx`). 공개 사이트에서 탭 이름 = 목록 화면 제목이 이미 성립한다.
- 하위 화면과 기타 문구는 최소 범위로 한정한다. 요청 4의 문장은 "탭 이름"과 "각 탭 진입 시 제목"만 지목한다. 하위 화면 제목·버튼·안내까지 영어화하면 admin 전체 현지화가 되어 사용자 요청 범위를 넘는다. 이 결정의 결과로 "blog" 목록 위에 "새 글" 같은 한글 하위 제목이 섞인다. 7절에서 사용자 확인을 받는다.
- `logout`은 `SignOutButton` 한 컴포넌트가 헤더(`admin-console-shell.tsx`)와 오류 알림의 행동 버튼(`form-parts.tsx`의 `signOut`)에서 함께 쓰인다. 같은 기능의 컨트롤 이름이 화면마다 다르지 않도록 컴포넌트 라벨 한 곳을 `logout`으로 바꾼다. 결과로 "권한이 없습니다." 옆 버튼도 `logout`이 된다.
- 6번째 탭 `logout`은 링크가 아니라 버튼이다(`signOut`). 라벨과 동작만 영어화하고 탭 형태로 바꾸지 않는다.

### 2.3 6번 삭제 범위

결정(권장안): DB 컬럼까지 제거한다. 코드 변경과 운영 마이그레이션을 분리해 순서를 고정한다.

| 영역 | 변경 |
| --- | --- |
| admin UI | `blog-form.tsx`의 "공개" 체크박스와 hint, draft의 `published` 필드, 삭제 모달 문구의 "공개 글이면" 조건 표현, .md 가져오기 안내의 "published" 언급 |
| admin 목록 | `blog/page.tsx` 행의 "공개/비공개" 표시 제거(날짜만) |
| API 입력 | `blog.schema.ts`의 `published` 제거(`strictObject`이므로 이전 번들이 보낸 `published`는 400이 됨, 5.2 참조) |
| 서비스 | `blog-service.ts`의 `eq(posts.published, true)` 조건(목록·카테고리 집계·단건) 제거, `toPostSummary`/`PostSummary.published` 제거, 공개/admin 읽기 함수가 동일해지면 통합(개발자 판단, knip 통과 필수) |
| .md import | frontmatter의 `published` 키를 읽지 않고 무시(`toc` 등 알 수 없는 키와 동일 취급). `frontmatter.ts`의 `published` 타입 검사와 오류 분기 제거 |
| 이관 스크립트 | `scripts/migrate-blog.ts`와 `__tests__/utils/migrate-script.test.ts` 등 `published`를 쓰는 곳 정리(이미 운영 이관 완료된 1회성 스크립트이나 컴파일이 깨지므로 갱신) |
| DB | `posts.published` 컬럼 삭제. `posts_list_idx`(published, published_at desc, slug desc)는 컬럼 삭제로 함께 사라지므로 `(published_at desc, slug desc)` 인덱스로 재정의 |
| 테스트 | `published`를 단언하는 기존 테스트(`blog-schema`, `blog-frontmatter` 등) 갱신, 삭제 후 요청에 `published`가 있으면 거부되는지 확인 |

근거:

1. 사실: 원본 `_posts`의 `published:` 보유 195개 모두 `true`, `false`는 0개이고 운영 DB 297행이 모두 공개다(00-input). 선행 requirements의 존치 근거("원본에 `published: false` 글이 실제로 있음")가 틀림이 확인되었다.
2. 컬럼을 남기면 모든 행이 항상 `true`인 죽은 컬럼과 항상 같은 값으로 필터링하는 인덱스 선두 컬럼이 스키마에 남는다. `db/schema/portfolio.ts`가 스키마의 단일 원본이므로, 코드에서 쓰지 않으면서 스키마에 남기는 것은 이 저장소의 "죽은 코드 금지" 방향(project-structure.md 5번)과 어긋난다.
3. 반대 쪽 위험은 운영 DB 쓰기다. 그래서 코드를 먼저 배포하고 마이그레이션을 나중에 적용하는 순서를 고정한다. 컬럼이 `NOT NULL DEFAULT true`라(`0003_purple_blur.sql`) 컬럼을 참조하지 않는 새 코드는 컬럼이 남은 DB에서도 insert가 성공한다. 반대 순서(컬럼을 먼저 삭제)는 이전 코드가 깨지므로 금지한다.
4. 최소 범위(UI·API 입력·.md import만 정리하고 컬럼 유지)를 대안으로 검토했다. 장점은 운영 DB 변경이 없다는 것이다. 단점은 위 2번과, 이후 컬럼 제거를 다시 별도 사이클로 처리해야 한다는 것이다. 사용자 지시가 "지워"이므로 컬럼 제거를 권장안으로 하고, 승인 게이트(5.3)에서 사용자가 최소 범위로 낮출 수 있게 둔다.

영향 기록:

- 공개 쿼리 조건: 목록, 카테고리 집계, 단건 조회 3곳의 `published = true` 조건이 사라진다. 모든 행이 공개 상태였으므로 결과 집합은 변하지 않는다(적용 전 `published = false` 행이 0건임을 확인).
- 인덱스: `posts_list_idx`가 선두 컬럼을 잃는다. 컬럼 삭제 시 이를 포함한 인덱스는 PostgreSQL이 함께 삭제하므로 마이그레이션이 `(published_at desc, slug desc)` 인덱스를 새로 만들어야 한다. 정렬 키는 현재 쿼리와 같은 `published_at desc, slug desc`다.
- 마이그레이션 번호: `drizzle/0004_*.sql`이 생성된다(현재 최신 0003).

## 3. 기능 분해와 수용 기준

우선순위: P0 = 이번 사이클 필수(요청 본문), P1 = 같은 사이클 권장(동작 안정성), P2 = 후속 가능.

### F1. 공개 Navbar 모바일 간격 (요청 1) (P0)

현재: 모바일 `flex-col items-start gap-8 py-16`, 주석상 높이 89px로 본문 시작 `--spacing-header` 92px 안에 맞춤(`navbar.tsx`, `globals.css`).

수용 기준:

1. 모바일(`md` 미만)에서 이름 줄과 링크 줄 사이 간격이 현재 8px보다 넓다. 값은 designer가 정하고 근거를 적는다.
2. 간격을 넓힌 뒤 Navbar 높이가 본문 시작 오프셋(`pt-header`)을 넘지 않는다. 넘으면 오프셋을 함께 늘린다. 이때 `--spacing-header`를 쓰는 모든 곳을 확인해 `md` 이상 레이아웃과 다른 페이지의 시작 위치가 의도 없이 변하지 않게 한다(개발자가 사용처 전수 확인, 변경 범위를 결과에 기록).
3. 320, 375, 390px 폭에서 링크 6개가 화면 밖으로 나가거나 가려지지 않는다.
4. `md`(768px) 이상 화면은 시각적으로 변하지 않는다.
5. 스크롤 후에도 fixed Navbar가 본문 첫 요소를 가리지 않는다.

Edge case: 이름이 긴 경우, 시스템 글꼴 크기 확대, 브라우저 최소 폭.

### F2. 공개 `/blog` 카테고리 탭 행간 (요청 2) (P0)

현재: `flex flex-wrap gap-x-16 gap-y-8 text-small`, 링크는 `text-small` 줄 높이(1.4)만큼의 높이(`blog/page.tsx`).

수용 기준:

1. 모바일에서 탭이 두 줄 이상으로 줄바꿈될 때 행 사이 간격이 현재보다 넓고, 각 링크가 위아래 이웃 링크와 시각적으로 분리된다.
2. 링크의 세로 터치 영역을 확보한다. 프로젝트 내 선례는 admin 탭(`min-h-44`)과 페이지네이션 디자인(`min-h-44 min-w-44`, design-spec 3.5)이다. 최종 값은 designer가 정한다.
3. 가로 간격, 활성 표시(밑줄, `aria-current`), 데스크톱 레이아웃은 변하지 않는다.
4. 같은 패턴이 admin 카테고리 탭(F5)에도 쓰이므로 두 곳의 간격이 일치한다.

Edge case: 카테고리 이름이 길어 한 줄에 하나만 들어가는 경우, 카테고리가 매우 많은 경우.

### F3. 글 하단 링크 정리와 이전/다음 글 (요청 3) (P0)

현재: 상단 링크(`blog 목록으로`)와 하단 링크(`mt-64`)가 모두 있다. 이전/다음 글은 선행 requirements에서 범위 밖이었고 이번에 추가한다.

세부 확정:

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 순서 기준 | 공개 목록과 같은 정렬 키 `published_at desc, slug desc` | `blog-service.ts` 목록 정렬. 같은 날짜 글도 slug로 결정적 순서 |
| 방향 | "이전 글" = 더 오래된 글(목록에서 뒤), "다음 글" = 더 최신 글(목록에서 앞). 링크에 글 제목을 표시해 방향이 방향어에만 의존하지 않게 함 | 시간 순서 기준 명명. 방향 반대 선호가 있으면 7절 |
| 카테고리 필터 | 무시. 전체 글 기준 | 상세 URL(`/blog/{slug}`)이 목록의 필터 상태를 갖지 않음 |
| 첫 글/마지막 글 | 해당 방향 링크 없음. 존재하는 쪽만 표시 | |
| 글이 1개뿐 | 이전/다음 영역 자체를 렌더링하지 않음 | |
| 위치 | 본문 아래. "blog 목록으로" 링크는 상단 하나만 | 사용자 확정(GOV.UK, NICE 근거는 00-input) |

수용 기준:

1. 하단의 "blog 목록으로" 링크가 제거되고 상단 링크는 그대로다.
2. 본문 아래에 `nav`(`aria-label` 지정)로 이전/다음 글 링크가 있다. 링크 이름은 방향어와 글 제목을 모두 포함한다.
3. 비교 키는 목록 정렬과 동일한 `(published_at, slug)` 튜플이고 DB 정렬과 같은 collation 규칙을 쓴다. 목록 순서와 이전/다음 순서가 어긋나지 않는다(테스트로 보장: 같은 날짜 3개 이상, 첫/마지막/중간 글).
4. 조회는 이웃 글의 `slug`, `title`만 가져온다(본문 제외). 상세 한 번당 추가 쿼리는 최대 2개다.
5. 한글 slug 링크가 올바르게 인코딩된다(기존 `encodeURIComponent` 방식).
6. 이전/다음 링크도 기존 블로그 링크처럼 `prefetch={false}`(`blog/[slug]/page.tsx`의 목록 링크와 동일 정책)를 따르고, 키보드 포커스 표시가 있다.
7. 빈 본문 글("본문이 없습니다.")에서도 이전/다음이 나온다.
8. 이전/다음 영역의 모바일 폭(375px) 레이아웃이 넘치지 않는다. 긴 제목은 줄바꿈된다.

Edge case: 같은 날짜 여러 글, 삭제된 글 사이 이동(조회는 항상 현재 DB 기준), 제목이 매우 긴 글, 직전 글이 삭제된 직후 캐시된 상세(admin 쓰기가 `revalidatePath`로 `/blog`와 `/blog/{slug}`를 갱신하는데 이웃 글 상세는 갱신 대상이 아니다. 글 추가/삭제 후 이웃 글 상세의 이전/다음 링크가 오래된 캐시를 보일 수 있으므로, 개발자가 갱신 방식을 확인하고 결과를 기록한다).

### F5. admin 블로그 목록 카테고리 탭 그룹 (요청 5) (P0)

현재: `/admin/blog`는 페이지네이션만 있고 카테고리 필터가 없다. 공개 `/blog`는 `?category=`와 `nav aria-label="카테고리"` 링크 목록을 가진다. 카테고리 집계 함수는 `listPublicCategories`(published=true 조건 포함)뿐이다.

세부 확정:

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 쿼리 방식 | 공개와 동일한 `?category=` 단일 값 | 같은 관례, 공유 가능한 URL, JS 불필요 |
| 정규화·검증 | 공개와 동일 규칙(트림, NFC, `POST_LABEL_MAX` 초과 시 필터 미적용, 배열이면 첫 값). 한 곳의 함수로 공유하고 복제하지 않음 | 두 목록의 해석이 갈라지지 않게 |
| 집계 기준 | admin 목록 기준(전체 글). F6 이후 공개 집계와 같은 집합이 된다 | 사용자 확정, F6 |
| 페이지네이션 조합 | `category`를 유지한 채 `page`만 변경. 카테고리 변경 링크는 `page`를 포함하지 않아 1페이지로 초기화 | 공개 목록 디자인(design-spec 3.4, 3.5) |
| "전체" | 첫 항목, 선택 해제 수단 | 공개와 동일 |
| 건수 문구 | 필터 시 "{카테고리} 카테고리 총 N개 중 a-b번째", 비필터 시 "총 N개 중 a-b번째" | 공개 목록의 부분 목록 표현과 동일(전체 개수와의 관계) |
| 표시 | 카테고리 이름만, 개수는 표시하지 않음(공개와 동일). 정렬은 개수 내림차순 후 이름 | 공개 `listPublicCategories` 정렬 |
| 빈 결과 | "이 카테고리에 글이 없습니다." + "전체 보기" 링크. 글 0개일 때는 기존 빈 상태 | 공개와 동일 |
| 행 | 제목과 날짜. "공개/비공개"는 F6으로 제거 | F6 |

수용 기준:

1. `/admin/blog`에 카테고리 `nav`가 보이고 `aria-current`로 현재 항목이 표시된다. 카테고리가 하나도 없으면 `nav`를 렌더링하지 않는다.
2. 카테고리 링크 클릭 시 해당 카테고리 글만 날짜 내림차순 50개씩 페이지네이션된다. 존재하지 않는 카테고리는 빈 상태를 보인다.
3. 페이지네이션 링크가 선택된 `category`를 유지한다.
4. 공개와 admin 카테고리 탭의 마크업, 간격(F2), 활성 표시가 일치한다. 공용 컴포넌트 추출 여부는 개발자가 정한다.
5. 글 생성/수정/삭제 후 목록으로 돌아오면 카테고리 집계가 갱신된 서버 렌더 결과로 보인다(캐시된 오래된 집계 금지).
6. 카테고리 필터와 "새 글" 진입점, 토스트("삭제했습니다.")가 함께 동작한다.
7. 쿼리 값은 파라미터화된 쿼리로만 사용한다(기존 방식 유지).
8. 범위를 벗어난 `page`, 숫자가 아닌 `page`는 기존 `parsePageParam`/clamp 규칙을 따른다.

Edge case: 카테고리 이름에 한글/공백/특수문자(퍼센트 인코딩), `category`가 여러 개, 카테고리 없는 글(필터에는 나타나지 않고 "전체"에서만 보임), 필터 결과가 50개 초과, 마지막 글을 삭제해 카테고리가 사라졌는데 URL이 그 카테고리를 가리킴(빈 상태 + 전체 보기).

### F6. 공개 여부 기능 삭제 (요청 6) (P0)

2.3의 결정을 따른다.

수용 기준:

1. 블로그 폼에 "공개" 체크박스와 "해제하면 공개 목록에서 즉시 사라집니다." 문구가 없다.
2. admin 목록 행에 공개/비공개 표시가 없다.
3. 생성/수정 API가 `published`를 받지 않는다. 포함된 요청은 검증 오류(400)로 거부되며 다른 필드는 영향 없다.
4. 공개 목록, 카테고리 집계, 상세, 이전/다음(F3) 쿼리 어디에도 `published` 조건이 없다. 사이클 완료 시점에 저장소 전체에서 `published`(글 공개 여부 의미)를 찾아 남은 곳이 없음을 개발자가 확인한다(`published_at`/`publishedAt`은 발행일이므로 별개).
5. .md 가져오기는 frontmatter의 `published` 값을 무시하고 오류도 내지 않는다(값이 `false`든 문자열이든 같음). 가져오기 안내 문구에서 `published` 언급을 지운다.
6. 삭제 확인 모달 문구에서 공개 여부에 따른 분기 표현("공개 글이면")을 지운다. 글이 삭제되면 공개 주소도 사라진다는 사실은 유지한다.
7. DB 컬럼 삭제 마이그레이션 `drizzle/0004_*.sql`이 생성되고 커밋된다. 마이그레이션은 인덱스 재정의를 포함한다. 새 인덱스는 `(published_at desc, slug desc)`다.
8. 적용 전 확인 쿼리로 `published = false` 행이 0건임을 확인한다(5.3).
9. `drizzle` 스키마(`posts`)와 SQL이 일치한다(`drizzle-kit` 생성 결과를 수정 없이 사용하거나, 수정했다면 사유를 기록).
10. 테스트: 입력 스키마가 `published`를 거부, frontmatter 파서가 `published`를 무시, 목록이 전체 행을 반환, 이관 스크립트 테스트 통과.

Edge case: `published: false` frontmatter를 가진 .md를 가져오면 저장 시 공개 글이 된다(삭제의 의도된 결과, 7-4 결정으로 가져오기 결과 토스트에 공개 전환 안내 포함), 이전 번들을 연 탭에서 저장하면 `published` 필드 때문에 400(5.2), 코드 배포 후 마이그레이션 적용 전 구간에도 읽기/쓰기가 정상(컬럼이 남아 있어도 코드는 참조하지 않음), `unique`·check 제약은 변하지 않음.

### F7. 마크다운 에디터 작성/미리보기 탭 UI (요청 7) (P0)

현재: `AdminButton` 두 개에 `aria-pressed`(`markdown-editor.tsx`). 선행 design-spec 6.4는 "작성/미리보기 탭"이었으나 구현이 토글 버튼이 되었다.

수용 기준:

1. 두 항목이 `role="tablist"` 안의 `role="tab"` 요소이고 `aria-selected`로 현재 상태를 나타낸다. 각 탭은 `aria-controls`로 패널(textarea 영역, 미리보기 영역)과 연결되고 패널은 `role="tabpanel"`과 탭 이름으로의 레이블을 가진다.
2. 시각 표현은 버튼이 아니라 탭이다. 기존 admin 탭(밑줄 + 불투명도)과 같은 방식으로 맞추며 최종 스타일은 designer가 정한다. 새 색 토큰은 만들지 않는다.
3. 키보드: 선택된 탭만 Tab 순서에 들어가고 좌/우 방향키로 탭 이동, Home/End 지원(designer·개발자가 선택 시 선택 동작을 확정하고 기록: 방향키 이동이 곧 선택인지 Enter/Space 선택인지).
4. 탭 전환 시 본문 값, 커서 위치, 스크롤 위치, 업로드 진행 상태가 보존된다(textarea는 현재처럼 언마운트하지 않고 숨김).
5. "이미지 삽입" 버튼은 탭 목록 밖에 있고 탭 의미에 섞이지 않는다.
6. 미리보기 탭 선택 상태에서 이미지 업로드가 끝나면 본문에 삽입되고 미리보기에 반영된다. 이때 숨겨진 textarea로 포커스를 옮기지 않는다(현재의 포커스 복귀는 작성 탭에서만 의미가 있다).
7. 라벨 문구는 한글 "작성", "미리보기"를 유지한다(F4는 탭 이름과 제목 한정).
8. 기존 `aria-pressed`는 제거한다.
9. 모바일(375px)에서 탭과 "이미지 삽입" 버튼이 한 줄 또는 줄바꿈으로 겹침 없이 배치된다.

Edge case: 빈 본문에서 미리보기("미리볼 내용이 없습니다."), 스크린리더에서 탭 이름과 선택 상태가 낭독됨, 업로드 중 탭 전환, 저장 중 탭 전환.

### F8. 본문 글자 수 표시 (요청 8) (P0)

현재: `hint`="마크다운. 최대 300,000자.", counter=`${value.length}자`(`markdown-editor.tsx`, `blog-form.tsx`).

수용 기준:

1. counter 문구가 `현재 / 300,000자` 형식이다. 숫자는 천 단위 구분(`3,700 / 300,000자`)이다. 상한값은 `POST_CONTENT_MAX`(`constants/blog.ts`)에서 가져오며 문구에 숫자를 새로 하드코딩하지 않는다.
2. 본문 hint 문구("마크다운. 최대 ...")가 없다. `describedBy`가 hint 없이도 올바른 `aria-describedby`를 만든다(오류 id만 연결).
3. props 변경: `BlogForm`이 `MarkdownEditor`에 상한 값(`POST_CONTENT_MAX`)을 `maxLength`로 넘기고, `MarkdownEditor`는 `hint` prop을 받지 않는다. 호출부는 `BlogForm` 하나다(개발자가 사용처 확인).
4. 현재 글자 수는 서버 검증(`z.string().max(...)`)과 같은 단위(JS 문자열 길이)로 센다. 두 값이 어긋나지 않는다(테스트).
5. 상한 초과 시 숫자는 그대로 표시되고(예: `300,001 / 300,000자`) 제출 시 기존 필드 오류가 입력란 아래에 나온다. 상한을 넘겨도 입력 자체는 막지 않는다(현재 동작 유지).
6. 다른 폼의 `TextAreaField` counter(`현재/최대`)는 바꾸지 않는다.
7. counter는 라이브 영역이 아니다(타이핑마다 낭독되지 않음, 현재와 동일).

Edge case: 이모지 등 서로게이트 쌍(길이 2로 계산, 서버와 동일), 0자("0 / 300,000자"), 로케일 구분 기호(항상 `,`), .md 가져오기 직후 갱신.

### F9. 결과 알림 토스트 통일 (요청 9) (P0)

2.1의 결정(범위·유지 규칙)을 따른다. 사용자 스크린샷의 "완료: 이미지를 본문에 넣었습니다. alt 텍스트를 확인하세요."도 토스트로 나온다.

수용 기준:

1. admin 콘솔 공통 영역(`AdminConsoleShell` 하위)에 토스트 표시 영역이 한 곳 있고, 2.1 표의 "토스트" 대상이 모두 이를 통해 나온다. 새 의존성은 추가하지 않는다. 컴포넌트 파일 위치와 이름은 개발자가 정하되 `project-structure.md`(kebab-case, `components/admin/`)를 따른다.
2. 성공 토스트: `role="status"`, 자동 소멸. 닫기 버튼과 소멸 일시정지(포인터, 포커스)를 제공한다. 소멸 시간은 designer가 정하고 근거를 적는다.
3. 오류 토스트: `role="alert"`. 닫기 전까지 유지된다(2.1). 링크(`다시 로그인`, `목록으로`)와 버튼(`logout`, `새로고침`) 행동이 붙으면 토스트 안에서 클릭/키보드로 동작한다.
4. 문구의 `완료:`/`오류:` 접두어는 색 의존을 피하기 위해 유지한다(기존 `FormStatus` 규칙).
5. `useAdminForm`이 notice를 폼 상태로 들고 있지 않고 토스트로 내보낸다. 기존 "성공 알림은 이후 편집이 시작되면 숨김" 동작(dirty 시 notice 숨김)은 토스트에서는 필요 없다(별도 소멸 규칙으로 대체, 이전 결과가 편집 중 화면에 남아 오해를 주지 않음).
6. `FormStatus`와 `FormActionBar`의 `notice`/`detailed` 요약 경로를 제거한다. 5개 폼 모두 같은 방식으로 정리하고 호출부 누락이 없음을 개발자가 전수 확인한다(`profile-form`, `project-form`, `talk-form`, `resume-entry-form`, `blog-form`).
7. `SortableList`의 순서 저장 성공, 삭제 완료, 오류(충돌 시 `새로고침` 버튼 포함)가 토스트로 나온다. 이동 안내 `aria-live`와 미저장 배너는 유지한다.
8. 목록 화면 4곳(projects, talks, resume, blog)의 "삭제했습니다."는 `?deleted` 도착 시 토스트로 나온다. 한 번 표시된 뒤 새로고침, 뒤로 가기로 다시 표시되지 않는다(P1: 현재는 `?saved=1`/`?deleted=1`이 URL에 남아 새로고침마다 다시 보임. 해소 방식은 개발자 결정).
9. 생성 후 편집 화면 이동(`?saved=1`), slug 변경 후 `router.replace`(project·talk) 등 토스트를 띄운 직후 화면이 바뀌는 경로에서도 토스트가 사라지지 않고 이동한 화면에서 보이거나 도착 화면이 새로 띄운다. 중복 표시도 없다.
10. 토스트는 포커스를 가로채지 않는다. 검증 실패 시 첫 오류 필드로 포커스 이동하는 기존 동작(`focusTick`)은 유지한다.
11. 한 번에 보이는 토스트 수에 상한을 둔다(빠른 반복 동작이 무한 누적되지 않음). 상한과 교체 규칙은 designer가 정한다.
12. 토스트는 하단 고정 `FormActionBar`(저장/취소/삭제 버튼)와 겹쳐 버튼을 가리지 않는다. 375px 폭에서도 동일하다(6절).
13. 키보드 사용자가 행동이 있는 토스트에 도달할 수 있다. 도달 방식(Tab 순서 위치 등)은 designer가 정하고 design-spec에 적는다.
14. 새 애니메이션을 추가하는 경우 `prefers-reduced-motion`을 존중한다. 애니메이션이 없어도 된다.
15. 기존 e2e/단위 테스트 중 "완료: 저장했습니다..." 등 이전 위치의 notice를 단언하는 것을 갱신하고, 토스트 소멸/유지 규칙(성공 소멸, 오류 유지, 일시정지)은 타이머 기반 단위 테스트로 검증한다.

Edge case: 연속 저장(성공 -> 즉시 실패), 저장 중 이미지 업로드 완료 토스트 겹침, 같은 메시지 반복 시 중복 토스트, 세션 만료(401) 시 `다시 로그인` 링크 토스트가 유지되고 `from` 경로가 맞음, 토스트가 떠 있는 상태에서 다른 admin 탭으로 이동, 목록 순서 저장 중 이탈 경고(F10)와 동시 발생, 토스트 표시 중 모달(F10)이 열림(모달 뒤로 가려지지 않아도 되나 모달 포커스 흐름을 깨지 않음).

### F10. `window.confirm`을 커스텀 모달로 통일 (요청 10) (P0)

현재 `ConfirmDialog`(`confirm-dialog.tsx`)는 삭제 전용이다(버튼 "취소"/"삭제", 진행 중 "삭제 중...", 삭제 버튼 `danger`). 이탈 경고와 확인 5곳은 `window.confirm`을 쓴다.

세부 확정:

| 항목 | 결정 |
| --- | --- |
| `ConfirmDialog` 일반화 | 확인 버튼 라벨, 진행 중 라벨, 확인 버튼 variant(danger/primary), 취소 라벨을 props로 받는다. 기본값은 지금 값("취소"/"삭제"/"삭제 중..."/danger)이라 기존 호출부 동작이 변하지 않는다. 기본 포커스가 취소 버튼인 동작도 유지 |
| 사용처별 문구 | 아래 표 |
| `beforeunload` | 브라우저가 커스텀 UI를 허용하지 않아 기본 창 유지(사용자 확정). `use-admin-form.ts`, `sortable-list.tsx` 모두 |

| 사용처 | 모달 | 확인 라벨 | 확인 동작 |
| --- | --- | --- | --- |
| `use-admin-form.ts` 링크 클릭 이탈 | "저장하지 않은 변경 사항이 사라집니다. 이동할까요?" | 이동 | 클릭했던 링크의 목적지로 이동 |
| `sortable-list.tsx` 링크 클릭 이탈 | "저장하지 않은 순서 변경이 있습니다. 변경을 버리고 이동할까요?" | 이동 | 클릭했던 링크의 목적지로 이동 |
| `sortable-list.tsx` 뒤로가기(popstate) | 위와 같은 문구 | 이동 | 사용자가 의도한 뒤로가기 수행 |
| `project-form.tsx` slug 변경 확인 | 기존 `/work/{이전} -> /work/{새}` 변경 안내문 유지 | 저장 | 저장 진행 |
| `talk-form.tsx` slug 변경 확인 | 기존 안내문 유지 | 저장 | 저장 진행 |
| `blog-form.tsx` .md 덮어쓰기 | "입력한 내용이 .md 파일 내용으로 바뀝니다. 계속할까요?" | 덮어쓰기(danger) | 가져온 내용을 폼에 반영 |

수용 기준:

1. 저장소 `src/` 전체에서 `window.confirm`, `window.alert`, `window.prompt`(및 전역 `confirm(`/`alert(`/`prompt(`) 사용이 `beforeunload` 핸들러 외에 없다. 개발자가 전수 검색한 결과(명령, 건수)를 구현 문서에 기록하고 QA가 재검색한다. 위 표 6곳 외 사용처가 나오면 같은 방식으로 포함한다.
2. 취소/닫기(Esc 포함)를 누르면 현재 화면과 입력 값이 그대로 유지되고 이동/저장/덮어쓰기가 일어나지 않는다. 확인을 누르면 표의 동작이 수행된다.
3. 이탈 경고(링크 클릭)는 `Link`로 만든 이동과 일반 `a`를 모두 가로챈다. 수정키/새 탭/다운로드/`#` 링크는 현재처럼 가로채지 않는다(현재 가드 조건 유지). 확인 후 이동할 때 `beforeunload` 기본 창이 한 번 더 뜨지 않는다(`sortable-list`의 `leavingRef` 방식이 선례).
4. 이탈 경고를 거쳐 이동하는 도중 `dirty`가 여전히 참이어도 같은 모달이 다시 뜨지 않는다.
5. 뒤로가기 경로(popstate, `SortableList`): 모달을 띄운 동안 현재 화면과 URL이 이탈 전 상태로 유지되고, 취소하면 그대로, 확인하면 사용자가 의도한 뒤로가기가 수행된다. 이 경로는 동기 `window.confirm`과 달리 브라우저/Next 라우터가 이미 이동을 처리할 수 있어 구현 위험이 크다. 개발자가 실제 브라우저(E2E)에서 검증하고, 안정적으로 만들 수 없으면 임의로 `window.confirm`을 남기지 않고 orchestrator에게 보고해 사용자 판단을 받는다(7절 위험).
6. `useAdminForm`의 폼은 현재 뒤로가기를 보호하지 않으며(`use-admin-form.ts` 주석의 한계) 이번에 추가하지 않는다.
7. slug 변경 확인(project·talk)은 현재처럼 검증보다 먼저 묻는다. 순서를 바꾸지 않는다. 취소하면 아무 것도 저장하지 않고 폼 값과 포커스를 유지한다. 확인하면 모달이 닫히고 저장이 진행되며 저장 중/결과는 평소 저장과 같이 표시된다(F9).
8. .md 덮어쓰기: 모달이 열린 동안 선택한 파일 내용을 보관하고, 취소하면 폼은 변하지 않으며, 확인하면 한 번만 반영한다. 파일 선택 input은 같은 파일을 다시 선택할 수 있게 값이 초기화된다(현재 동작).
9. 모달은 `role="dialog"` 이름(`aria-labelledby`)과 설명, 포커스 가둠, 닫을 때 원래 트리거로의 포커스 복귀 등 네이티브 `dialog`가 제공하는 동작을 유지한다.
10. 삭제 모달 문구와 동작(진행 중 비활성, 실패 시 모달 내 오류)은 변하지 않는다(F6의 "공개 글이면" 문구 정리 제외).
11. 단위/E2E: 기본값 호출부(삭제)가 회귀하지 않음을 확인하고, 새 사용처마다 취소/확인 경로 각각을 테스트한다.

Edge case: 모달이 열린 상태에서 새로고침(`beforeunload` 기본 창), 모달 확인 직후 이동 실패, 이탈 모달이 열린 동안 저장이 끝남, 연속 클릭으로 모달 두 개 요청, 삭제 모달이 열린 상태에서 링크 클릭(모달 뒤는 비활성), 모바일에서 모달 높이.

### F11. 저장 후 이동 동작 유지와 결과 토스트 (요청 11) (P0)

동작 변경 없음. 결과 표시만 F9로 바뀐다.

수용 기준:

1. 편집 화면에서 저장하면 같은 화면에 남고 토스트로 "저장했습니다. 공개 페이지에 반영되었습니다."가 나온다.
2. 생성 후에는 현재처럼 만든 항목의 편집 화면으로 이동하고(`router.push`), 도착한 화면에서 같은 저장 완료 토스트가 나온다.
3. 삭제 후에는 현재처럼 목록으로 이동하고 목록에서 "삭제했습니다." 토스트가 나온다.
4. 블로그, 프로젝트, 발표, 이력, 프로필 모두 같다. 프로필은 단일 화면이라 이동 없이 토스트만 나온다.
5. 어떤 경로에서도 새 이동 로직을 추가하지 않는다.

Edge case: 저장 실패 시 이동 없이 오류 토스트와 입력값 유지, 생성 후 이동 중 사용자가 다시 저장 클릭(`savingRef` 중복 제출 방지 유지), 이동 대상이 404.

## 4. 비기능 요구사항

- 접근성: 토스트 `role`, 닫기 버튼 이름, 키보드 도달성(F9), 탭 패턴(F7), 모달 포커스(F10), 모든 새 상호작용 요소의 포커스 표시(`focus-visible:outline-2 focus-visible:outline-white` 선례).
- 일관성: Tailwind 토큰만 사용하고 spacing은 px 환산(`tailwind.md`). 새 색 토큰은 만들지 않는다. 새 값이 필요하면 `globals.css`의 `@theme`에 토큰으로 추가한다.
- 성능: 이전/다음 조회는 본문을 읽지 않는다. 카테고리 집계는 기존 쿼리 구조를 유지한다.
- 의존성: 신규 패키지 추가 없음(토스트 포함). knip 통과.
- 코드 규칙: 파일명 kebab-case, 서버 전용 모듈 `import "server-only"`, HTTP 상태 코드는 `HttpStatusCode`, 주석·문서 em-dash 금지와 주석 종결/줄바꿈 규칙(`project-structure.md`).
- 테스트: slug 순서 비교(F3), 입력 스키마의 `published` 거부(F6), frontmatter `published` 무시(F6), 토스트 소멸/유지(F9), 글자 수 형식(F8), `ConfirmDialog` 기본값 회귀와 신규 경로(F10), 탭 접근성(F7)을 자동 테스트로 둔다. 기존 e2e의 탭 라벨, notice 문구 단언을 갱신한다.
- 반응형: 320, 375, 390, 768px 이상에서 F1, F2, F4, F7, F9, F10 레이아웃을 확인한다.

## 5. 배포와 운영 데이터, 승인 지점

### 5.1 배포 경로와 트리거

- 경로: `feature/admin-blog-ux` -> `develop`(Preview) -> `main`(Production). 병합은 `--no-ff`만, 사용자 지시 후(`branch-strategy.md`).
- 새로 능동적으로 발생하는 기능(알림/생성)은 없다. 토스트와 모달은 모두 사용자 액션이 트리거이고, 이전/다음 글은 상세 페이지 조회 시 서버 렌더에서 계산된다. 크론과 신규 환경변수는 없다.

### 5.2 코드와 마이그레이션 순서

1. 컬럼을 참조하지 않는 새 코드를 먼저 배포한다. 컬럼은 `NOT NULL DEFAULT true`라 새 코드의 insert가 성공한다.
2. 이후 마이그레이션 `0004`를 적용한다.
3. 반대 순서는 금지한다. 컬럼이 먼저 삭제되면 이전 코드의 쿼리가 깨진다.
4. 코드 배포 직후, 이전 번들을 열어 둔 admin 탭에서 저장하면 `published` 필드 때문에 400이 난다(입력 스키마가 `strictObject`). 새로고침으로 해소되며 운영자가 1명이라 허용한다. 구현 문서에 이 동작을 기록한다.
5. 마이그레이션을 어떤 경로(CLI, 배포 훅)로 적용하는지는 선행 사이클 실행 결과(`docs`/artifacts의 운영 이관 기록)를 개발자가 확인해 따른다. 이 문서는 적용 방법을 정하지 않는다.

### 5.3 승인 지점 (사용자 확인 필수)

| 지점 | 내용 |
| --- | --- |
| 요구사항 게이트 | T02 완료 후 이 문서에 대한 사용자 확인 |
| 운영 DB 마이그레이션 | `0004` 운영 적용 전 사용자 확인. 적용 전 `select count(*) from posts where published = false`가 0임을 확인(읽기 전용)하고, 0이 아니면 중단하고 보고. 다른 세션의 DB 작업 여부를 확인하고 `git-safety.md` 조율 절차를 따른다 |
| 로컬/개발 DB | 개발/테스트용 DB에서의 마이그레이션 검증은 승인 없이 진행 가능. 단 어떤 DB인지 연결 문자열을 확인하고 운영이 아님을 확인 |
| 커밋·병합 | 사용자 지시 후 `git-commit` Skill로 진행 |

롤백: 컬럼 재추가는 `ALTER TABLE posts ADD COLUMN published boolean NOT NULL DEFAULT true`이며 모든 행이 `true`였으므로 데이터 손실은 없다. 인덱스는 이전 정의로 되돌린다. 구현 문서에 롤백 SQL을 남긴다.

## 6. Bug Team 피드백 반영

출처: `artifacts/bug-team/2026-10-13-admin-save-feedback/postmortem.md` (00-input에서 인용).

- 기준: "행동 버튼이 고정 영역에 있으면 결과 피드백도 같은 영역에 둔다. 다른 위치에 두는 설계는 설계 산출물에 그 이유를 적는다."
- 이번 9번(토스트)은 결과 표시 위치를 하단 고정 `FormActionBar`에서 뷰포트 고정 토스트 영역으로 바꾼다. 위치는 "다른 위치"에 해당하므로 아래를 요구한다.

수용 기준:

1. design-spec에 "결과 피드백 위치" 항목을 두고, 토스트가 뷰포트 고정이라 본문이 아무리 길어도 스크롤 없이 보인다는 점을 근거로 이 기준을 충족함을 적는다(본문 3,000줄 입력 후 맨 위로 스크롤한 상태에서 저장 실패 시 추가 스크롤 없이 결과가 보임, 선행 design-spec 7절의 테스트 기준을 계승).
2. 토스트 위치가 하단 고정 저장 영역과 겹치지 않아야 한다(F9-12). 겹치면 사용자가 저장/삭제 버튼을 누르다 결과를 가리게 되어 원 버그의 반대 형태가 된다.
3. 저장 버튼을 누른 직후 결과가 같은 시야 안에 나타나는지 모바일 375px에서 확인한다(QA).
4. code-review에서 위 확인 결과를 남긴다.
5. 같은 포스트모텀의 미반영 항목(designer.md, code-reviewer.md 하네스 변경, "`FormStatus` 사용 파일은 `FormActionBar`에 `notice` 전달" lint 테스트)은 `feature/admin-form-feedback-guard` 대상이라 이번 범위 밖이다. 단 이번 변경으로 `FormStatus`가 삭제되고 `FormActionBar`의 `notice` prop이 없어지므로 그 lint 테스트의 불변식 자체가 성립하지 않게 된다. 결과 요약(summary)에 이 사실을 기록해 해당 브랜치에서 불변식을 토스트 기준으로 다시 정의하도록 한다. 포스트모텀 파일은 삭제하지 않는다.

## 7. 사용자 확인 결과 (2026-10-15 T02 게이트)

1. 영어화 범위(2.2): 최소 범위 확정. 탭 이름과 목록 화면 제목, metadata만 영어로 바꾸고 하위 화면 제목·버튼·안내는 한글 유지.
2. 일반 오류 토스트 유지(2.1): 기본값 확정. 행동이 없는 오류도 사용자가 닫을 때까지 유지하고, 다음 시도에서 치운다.
3. 이전/다음 방향(F3): 기본값 확정. 이전 = 더 오래된 글, 다음 = 더 최신 글.
4. `published: false` .md 가져오기(F6): **경고 추가로 확정**. frontmatter에 `published: false`가 있는 파일을 가져오면 가져오기 결과 토스트에 "이 파일은 비공개(published: false)였지만 저장하면 공개 글이 됩니다." 취지의 안내를 포함한다. 수용 기준: `published: false` 파일 가져오기 시 안내가 보이고, `published` 키가 없거나 `true`면 보이지 않는다.
5. 컬럼 제거(2.3): 컬럼 제거 확정. 운영 DB `0004` 적용은 별도 승인 게이트를 거친다.
6. popstate 모달화(F10-5): 구현자가 모달로 시도하고, 안정적으로 만들 수 없으면 임의로 `window.confirm`을 남기지 않고 orchestrator에 보고한다.
7. `window.confirm` 재발 방지 테스트: **포함으로 확정**. `enforcement-placement.md` 기준 전체 코드베이스 불변식이라 유닛 테스트(`__tests__/lint/`)로 둔다. 불변식: `src/`의 소스에 `window.confirm`, `window.alert`, `window.prompt` 호출이 없다(테스트 파일 제외). Task 계약상 신규 테스트이므로 T09 QA가 작성한다. 수용 기준: 현재 코드(구현 후)에서 통과하고, 임시로 호출을 넣으면 실패한다.
