- 작업 브랜치: `feature/project-thumbnails`
- 입력: `artifacts/task-team/requirements.md` (11절 A/E 확정, 13절 D1~D4 확정이 8·9절 제안보다 우선), `artifacts/task-team/api-spec.md` (끝의 "부록. 사용자 결정 반영" 우선)

## 2. 사용자 흐름

### 2.1 방문자

1. 홈 또는 `/projects`에서 카드를 본다. 단일 썸네일이면 이전과 동일하다(`/projects` lg 이상은 16:9 카드로 보임).
2. 복수 장이면 카드가 화면에 보이는 동안 4초마다 다음 이미지로 크로스페이드된다. 마지막 다음은 첫 장.
3. 마우스를 올리거나 키보드로 카드에 포커스하면 전환이 멈추고, 벗어나면 다시 4초부터 센다.
4. 창 폭이 768px을 넘나들면 새로고침 없이 맞는 목록으로 바뀐다. 바뀐 쪽은 첫 장부터 시작한다.
5. OS에서 "동작 줄이기"를 켠 사용자는 첫 장만 본다.

### 2.2 관리자

1. 프로젝트 편집 화면의 "썸네일" 영역에서 "기본 썸네일"과 "모바일 썸네일" 두 목록을 본다.
2. "썸네일 추가"를 누르면 빈 행이 생기고 파일을 고르면 업로드된 뒤 미리보기가 나온다.
3. 행의 위/아래 버튼으로 순서를 바꾸고(순서가 전환 순서), 삭제 버튼으로 행을 지운다.
4. 저장하면 공개 화면에 반영된다. 모바일 목록이 비어 있으면 모바일도 기본 목록을 쓴다.

## 3. 공개 카드 구조 (`ProjectCard`)

### 3.1 props 변경

- 기존 `thumbnail?: string`을 대체하는 값: PC(기본) 목록 `string[]`, 모바일 목록 `string[]`(둘 다 순서 있는 배열, 빈 배열 허용).
- 홈(`src/app/(public)/page.tsx`)과 `/projects`(`src/app/(public)/projects/page.tsx`) 두 호출부에서 둘 다 전달한다. 한쪽만 바꾸면 누락되므로 T05에서 두 파일을 함께 확인한다.
- 6절(D3) 때문에 `/projects` 호출부에만 켜는 불리언 옵트인 prop 하나를 추가한다(기본 꺼짐, 이름은 T05가 정함, 이 문서에서는 "와이드 변형"이라 부름). 켜면 lg 이상에서 카드 안 제목·패딩 크기가 달라진다. 홈 호출부는 전달하지 않는다.
- `preserveThumbnailText`, `eager`, `className`, 테마 props는 그대로.

### 3.2 실효 세트 계산 (서버, ProjectCard 내부)

입력 정규화: 빈 문자열 제거(서버 검증이 이미 보장하나 방어).

| 조건 | 실효 구성 | 렌더 경로 |
| --- | --- | --- |
| 기본 목록 비어 있음 | 썸네일 없음 | 현재와 동일(테마 배경색·글자색, 이미지 블록 없음) |
| 모바일 비어 있음 또는 모바일 == 기본 | 세트 1개(기본 목록) | 기본 1장이면 경로 A, 2장 이상이면 경로 B |
| 모바일 목록이 기본과 다름 | 세트 2개(PC, 모바일) | 경로 C |

- 경로 A (단일 세트 1장, 서버만): 현재 마크업 그대로. 바깥 `absolute inset-0` 래퍼, `preserveThumbnailText`용 컨테이너 래퍼, `Image fill sizes="(min-width: 1024px) 60vw, 100vw" loading=eager|lazy className="object-cover"`, 그라디언트 오버레이, 텍스트 블록, `alt="{title} 프로젝트 썸네일"`까지 문자열 단위로 동일해야 한다. 이 경로에는 타이머·옵저버·`"use client"` 컴포넌트가 없다(AC-R1~R4, R6).
- 경로 B (단일 세트 2장 이상): 같은 래퍼 구조 안의 이미지 자리에 전환 컴포넌트 하나. 숨김 래퍼 없음.
- 경로 C (세트 2개): 같은 래퍼 구조 안의 이미지 자리에 PC 세트와 모바일 세트를 형제로 둔다.
  - PC 세트 래퍼: `absolute inset-0 hidden md:block`
  - 모바일 세트 래퍼: `absolute inset-0 md:hidden`
  - 각 세트는 1장이면 정적 이미지, 2장 이상이면 전환 컴포넌트.
  - 정적 이미지(1장)는 서버 렌더, 전환 컴포넌트만 클라이언트.
  - `preserveThumbnailText`가 켜진 카드는 컨테이너·정사각 래퍼가 모바일 세트 래퍼 안쪽에만 생기고 PC 세트에는 없다(3.3절).

그라디언트 오버레이(`bg-linear-to-t from-black/70 from-50% to-transparent`)와 텍스트 블록은 모든 경로에서 세트 바깥, 세트 위에 그대로 한 번만 둔다. 세트 안에 넣지 않는다(전환 중 그라디언트가 같이 페이드되어 텍스트 가독성이 흔들리는 것 방지). 와이드 변형에서도 그라디언트 클래스는 바꾸지 않는다(6.3절 계산).

### 3.3 `preserveThumbnailText` 보존과 D4 (모바일 세트 한정)

규칙: `preserveThumbnailText`는 "모바일 세트에만" 적용한다. 1차본의 "모든 세트에 적용"은 폐기한다.

| 상황 | preserve 적용 위치 |
| --- | --- |
| 단일 세트(경로 A·B, 모바일 목록이 비었거나 기본과 같음) | 현재와 동일. 세트 전체에 컨테이너 래퍼(`containerType: size`), `min(100%, 100cqh)` 폭 중앙 정렬 래퍼, 이미지 `objectPosition: top`. DOM 변동 없음(AC-R3) |
| 세트 2개(경로 C) | 모바일 세트 래퍼(`absolute inset-0 md:hidden`) 안쪽에 컨테이너 래퍼와 정사각 래퍼를 두고 이미지에 `objectPosition: top`. PC 세트 래퍼(`absolute inset-0 hidden md:block`) 안에는 컨테이너·정사각 래퍼 없이 이미지를 `fill` + `object-cover`(object-position 기본)로 둠 |

- D4 데이터 적용 후 Candanta는 PC 목록 새 16:9 이미지 1장, 모바일 목록 기존 썸네일 1장이라 경로 C이며 두 세트 모두 정적 이미지(전환 없음)다. 모바일 세트는 현재 렌더(정사각 가운데, 상단 정렬)와 같은 모양, PC 세트는 일반 cover.
- `containerType: size`는 크기가 확정된 요소에만 걸린다. 모바일 세트 래퍼가 `absolute inset-0`이라 문제 없다. `md:hidden`으로 가려진 동안은 박스가 없으므로 컨테이너도 계산되지 않는다(다시 보이면 재계산).
- 모바일 세트에 복수 장이 들어와도 같은 래퍼 안에서 전환 컴포넌트가 동작한다(모바일 세트는 어차피 `object-top`). 이 조합의 시각 검수는 범위 외.
- 주의(과도기): D4 데이터가 반영되기 전, 또는 관리자가 Candanta의 기본·모바일 목록을 같은 값으로 저장해 단일 세트가 되면 preserve가 세트 전체에 걸린다. 이때 `/projects` lg 이상 카드는 16:9(약 687x386)라 정사각 영역이 약 386x386이 되어 좌우 각 약 150px에 카드 배경색이 보인다. 홈과 lg 미만은 기존과 동일. 이 모습은 코드 결함이 아니라 위 규칙의 결과이며 D4 데이터 반영으로 사라진다. 9절에 알림 항목으로 올림.

### 3.4 `sizes`와 로딩 전략

- PC 세트(또는 경로 A·B의 단일 세트): 기존 값 `(min-width: 1024px) 60vw, 100vw` 유지. 경로 A·B의 단일 세트는 `md` 미만에서도 같은 이미지를 쓰므로 값을 바꾸지 않는다(회귀 0). `/projects` lg 이상 카드는 7/12 컬럼(1440에서 약 48vw)이라 60vw는 약간 크게 받는 보수적 값이며, 16:9 변경으로 필요 폭이 줄지 않으므로 그대로 둔다(AC-R6).
- 모바일 세트(경로 C 한정): `100vw`. 모바일 뷰(768 미만)에서 카드는 사실상 뷰포트 폭이라 PC용 큰 변형을 받지 않는다.
- `eager`/`lazy`:
  - 경로 A, B: 기존과 같이 `eager`면 첫 장만 eager. 경로 B의 나머지 프레임은 항상 lazy.
  - 경로 C: 모든 프레임 lazy. 이유는 3.5.
- 대형 프레임 로딩 최소화: 전환 컴포넌트는 SSR에서 첫 장만 렌더한다. 이후 "현재 프레임과 다음 프레임"까지만 마운트하고, 한 번 마운트한 프레임은 유지한다(10장을 한꺼번에 받지 않음, 다음 장이 빈 화면으로 나오는 것도 방지 - E-h). reduced-motion이면 첫 장 외 프레임은 마운트하지 않는다.

### 3.5 숨겨진 세트의 불필요 다운로드 최소화 (AC-5)

- 경로 C에서 가려진 세트의 `<img>`는 `display: none` 서브트리에 있다. `loading="lazy"` 이미지는 렌더 박스가 없으면 뷰포트 교차가 일어나지 않아 브라우저가 받지 않는다. 그래서 경로 C의 모든 프레임을 lazy로 둔다.
- eager 이미지는 `display: none`이어도 받아 오므로 경로 C에서 eager를 쓰면 반대 뷰 이미지까지 내려받는다. 이것이 경로 C 전 프레임 lazy의 이유다.
- 트레이드오프: 경로 C의 첫 카드는 eager가 아니라 LCP가 약간 늦어질 수 있다(뷰포트 안 lazy 이미지는 레이아웃 직후 요청됨). T09에서 첫 카드가 SEMT인 상태로 네트워크 탭과 LCP를 확인하고, 문제가 되면 대안으로 첫 프레임만 `<picture>` 아트 디렉션(`next/image`의 `getImageProps`, `media="(min-width: 768px)"` source)으로 바꿔 eager 하나만 받게 한다. 이 대안은 디자인 변경 없이 마크업만 바뀌므로 T05가 판단해 보고한다.
- 위 동작은 일반 브라우저 동작에 근거한 설계이며 이 단계에서 실측하지 않았다. T09 네트워크 탭 검증 항목으로 남긴다.
- SSR/hydration: 뷰포트를 JS로 읽지 않는다. 서버 HTML에는 두 세트(경로 C)의 첫 장이 들어 있고 CSS가 뷰를 고른다. 전환 컴포넌트의 인덱스 초기값은 항상 0이라 서버와 첫 클라이언트 렌더가 같다. 깜빡임 없음(AC-4). `matchMedia`는 마운트 후 effect에서만 읽는다.

## 4. 전환 동작 명세

### 4.1 상수 (전역 고정, E4)

| 값 | 설정 |
| --- | --- |
| 노출 간격 | 4000ms |
| 크로스페이드 | 600ms, ease-in-out 계열 |

상수는 `src/constants/`의 한 곳에 둔다(두 값이 CSS 지속시간과 타이머에서 함께 쓰이므로 불일치 방지).

### 4.2 레이어와 크로스페이드

- 세트 안에서 프레임은 모두 `absolute inset-0`로 겹쳐 쌓는다. 각 프레임은 `Image fill` + `object-cover`(+모바일 세트는 `object-top`).
- 상태: 현재 프레임, 직전 프레임.
  - 새 프레임이 위 레이어에서 opacity 0에서 1로 600ms 동안 올라온다.
  - 직전 프레임은 opacity 1로 아래에 남겨 두고, 전환이 끝난 뒤 불투명도를 0으로(트랜지션 없이) 내린다.
- 이렇게 하는 이유: 두 레이어를 동시에 반투명으로 교차시키면 이미지가 불투명이어도 중간 구간에 카드 배경색이 비쳐 어두운 점멸이 생긴다.
- 호버 확대는 카드(`Link`)의 transform이라 레이어와 충돌하지 않는다. 확대 중에도 전환 가능하지만 호버 시 일시정지라 실사용에서는 겹치지 않는다(E-f).

### 4.3 타이머와 일시정지

- 조건이 모두 참일 때만 동작한다. 하나라도 거짓이면 타이머를 해제한다.
  1. 세트 프레임이 2장 이상(1장이면 전환 컴포넌트를 쓰지 않으므로 사실상 항상 참)
  2. `prefers-reduced-motion: reduce`가 아님
  3. 세트가 화면에 보임(IntersectionObserver 교차 상태, 렌더 박스가 없는 숨김 뷰는 교차 아님)
  4. 문서가 보이는 상태(`visibilitychange`)
  5. 호버 중이 아님(마우스·펜만 대상, 터치의 에뮬레이션 호버는 무시해 탭 뒤 정지가 남지 않게 함)
  6. 카드 링크 내부에 포커스가 없음
- 다음 프레임 호출은 "한 번 예약 후 실행되면 다시 예약" 방식이라 탭 복귀 때 누적 점프가 없다(AC-10). 일시정지 해제 시 남은 시간 이어가기가 아니라 4초를 처음부터 센다(구현 단순, 사용자 체감 차이 없음).
- 호버·포커스 이벤트는 카드 링크(조상 `a`)를 대상으로 한다. 링크 자체에 클래스를 더하지 않아 경로 A의 링크 클래스가 바뀌지 않는다. 단 `/projects` 호출부의 `className`에 6.2절 클래스가 더해지는 것은 D3 의도 변경이다.
- 뷰 전환(PC와 모바일 폭 넘나듦) 시: 세트가 숨김에서 보임으로 바뀔 때(옵저버 항목의 박스 크기 0에서 양수) 인덱스를 0으로 초기화하고 타이머를 새로 건다. 타이머는 세트당 최대 1개이며 언마운트 시 해제된다(AC-11). 화면 밖 스크롤로 인한 비교차는 인덱스를 초기화하지 않는다(박스 크기가 0인 경우만 뷰 전환으로 간주).
- 홈에 카드가 여러 개여도 각 세트는 자기 상태만 갱신하므로 다른 카드는 리렌더되지 않는다(AC-13). 화면 밖 카드는 타이머가 멈춰 있다.

### 4.4 reduced-motion

- 방문 중 설정이 바뀌어도 반응한다(변경 이벤트 구독).
- reduce이면 타이머 없음, 인덱스 0 고정, 직전 프레임 레이어 없음, 첫 장 외 프레임 미마운트. 단일 렌더와 시각적으로 동일하다(AC-8).
- 기존 카드의 `motion-reduce:transition-none` 관례와 같은 방향이다.

### 4.5 접근성 처리 (AC-12)

- 현재 보이는 프레임에만 `alt="{title} 프로젝트 썸네일"`을 둔다. 그 외 모든 프레임은 `alt=""` + `aria-hidden="true"`.
- 경로 C의 숨겨진 세트는 `display: none`이라 접근성 트리에서 빠진다. 보이는 세트의 현재 프레임 하나만 노출된다.
- 전환 알림용 `aria-live`는 쓰지 않는다. 모든 프레임의 alt 문구가 같아 링크의 접근 가능한 이름이 전환 때 바뀌지 않고, 자동 갱신 낭독은 방해가 된다.
- 포커스 링(`focus-visible:ring-2 ...`)은 링크 그대로 유지.
- 알려진 한계(요구사항 11절 예외 기록): 5초 넘게 움직이는 콘텐츠에 대한 포커스와 무관한 일시정지 수단(WCAG 2.2.2)은 사용자 결정으로 제공하지 않는다. 대신 호버·포커스 일시정지, reduced-motion 중지, 화면 밖 정지로 완화한다.
- 이미지 로드 실패(E-d): 실패한 프레임은 순환에서 건너뛴다. 세트의 모든 프레임이 실패하거나 첫 장이 실패하면 카드 배경색이 그대로 보이고 레이아웃은 유지된다(카드 높이는 `h-card` 계열 고정 또는 `/projects` lg 이상에서는 비율 고정, AC-15).

### 5.1 관찰 (실제 이미지 확인)

- 모바일 3장(03-03, 02-02, 04-04): 1290x2796(약 0.46:1). 세로 위치(이미지 높이 대비 %)는 근사값이다.

  - 약 30% 이후: 폰 목업 패널. 화면 내용은 약 33~90%, 하단은 탭 바.
  - 02-02와 04-04는 폰이 기울어져 있고, 03-03도 약간 기울어져 있다. 세 장 모두 상단 텍스트 구성이 같다.

### 5.2 모바일 카드 크롭 계산

모바일 카드는 폭이 뷰포트 폭에서 컨테이너 패딩을 뺀 값이고 높이는 `h-card`(60vh)다. `object-cover`는 폭 기준으로 확대해 세로를 자른다.

| 뷰포트 | 카드(약) | 이미지가 보이는 세로 비율 |
| --- | --- | --- |
| 375x812 | 327x487 | 약 56% (top 기준 0~56%) |
| 390x844 | 342x506 | 약 55% |
| 600x1000 | 552x600 | 약 40% |

- `object-position: top`이면 이 구간에서 로고, 헤드라인, 부제, 폰 상단이 항상 포함된다(약 26%까지의 텍스트가 모든 구간에서 보임).
- `center`이면 위 20% 안팎이 잘려 로고와 헤드라인 첫 줄이 사라진다. 이미지의 핵심 메시지가 헤드라인이므로 부적합하다.
- 카드 하단 그라디언트(아래 50% 구간에서 검정 70%)와 하단 정렬 제목·역할·기간 텍스트는 폰 목업 하단부를 덮는다. 폰의 하단은 탭 바 장식이라 가려져도 손실이 적고, 헤드라인과 부제는 카드 중간선 위에 있어 그라디언트 영향이 작다. 흰 글자 가독성(AC-14)이 유지된다.

### 5.3 결정

- 모바일 세트의 모든 프레임에 `object-position: top`(`object-top`, 기존 `object-cover` 유지).
- 알려진 한계: 가로 방향 모바일(예: 667x375, 카드 높이 약 225px)에서는 보이는 세로가 이미지의 약 15%라 로고와 헤드라인 일부만 보인다. 이 구간은 허용하고 `object-top`을 유지한다(별도 값을 두면 데이터 없이 판단하게 됨).
- 모바일 목록에 가로형 이미지가 올라와도 `object-top`은 세로 방향만 영향을 주므로 문제 없다.
- 모바일 뷰는 768 미만이고 D3 변경(lg 이상)과 겹치지 않으므로 5절 계산은 그대로 유효하다.

### 6.2 클래스 수준 명세 (구현자 적용용)

spacing 1 = 1px, 색은 흑백 팔레트와 기존 토큰만 사용. 새 색 없음. 새 토큰 없음(`@theme` 변경 없음).

**(a) `Link` (카드 루트)**

기본 클래스(변경 없음): `sticky top-160 block w-full h-card md:h-card-stuck rounded-lg overflow-hidden transition-transform hover:scale-[1.02] motion-reduce:transition-none motion-reduce:hover:scale-100 focus-visible:ring-2 ...`

`/projects` 호출부 `className` (현재 `h-card lg:h-card-tall`)를 다음으로 교체:

`h-card lg:aspect-video lg:h-auto lg:@container`

(`h-card`는 기본 클래스와 중복이라 지워도 동작은 같다. 지우는 것은 T05 판단.)

tailwind-merge 관계(`cn`은 `twMerge(clsx(...))`, 호출부 `className`이 기본 뒤에 합쳐짐):

| 클래스 | 병합 결과 |
| --- | --- |
| `h-card` | 기본의 `h-card`와 같은 그룹, 같은 값. 하나만 남음 |
| `lg:h-card-tall` | 삭제. 남기면 16:9 대신 75vh가 이김 |
| `lg:h-auto` | 기본의 `md:h-card-stuck`과 변형이 달라(`md:` vs `lg:`) 둘 다 남는다. 생성 CSS에서 `lg`가 `md` 뒤에 나오므로 1024 이상에서 `lg:h-auto`가 이김. 높이가 auto여야 `aspect-ratio`가 적용됨(MDN: 폭과 높이 중 하나는 auto여야 비율이 효력을 가짐) |
| `lg:aspect-video` | 충돌하는 기본 클래스 없음. 16/9 |
| `lg:@container` | 충돌 없음. 내부 `cqi` 단위의 기준 컨테이너(inline-size)를 만듦. 1024 미만에는 containment가 생기지 않아 하위 구간 스타일이 변하지 않음 |

- Tailwind 공식 문서에는 `@container`를 중단점 변형(`lg:`)과 붙여 쓰는 예가 없다. T05는 생성 CSS에서 `lg:@container`가 동작하는지 확인하고, 안 되면 `@container`를 무조건 붙인다(`w-full`이라 하위 구간 시각 변화는 없어야 하며 스크린샷으로 확인). 둘 다 컨테이너 포함 때문에 `sticky`가 깨지는지 `/projects` lg에서 스크롤로 확인한다.
- 카드 높이가 비율에서 나오므로 `75vh`와 뷰포트 높이 의존이 사라진다. `sticky top-160`은 그대로이며 행 높이가 카드 높이 이상이라 스티키 동작은 유지된다.

**(b) 카드 안 텍스트 블록 (와이드 변형이 켜진 경우만, `ProjectCard` 내부)**

twMerge가 `lg:text-6xl`과 임의 값 `lg:text-[...]`을 같은 그룹으로 판정하지 못할 수 있다(`text-[...]`는 값에 따라 색으로 오판됨, 아래 웹 검색 기록 8). 그래서 "덧붙여 병합"이 아니라 와이드 변형 여부에 따라 둘 중 하나를 고르는 조건 분기로 적용한다.

| 요소 | 와이드 변형 꺼짐(홈, 기본) | 와이드 변형 켜짐(`/projects`) |
| --- | --- | --- |
| 텍스트 블록 컨테이너 | `p-32 md:p-48 lg:p-64` | `p-32 md:p-48 lg:p-[clamp(1.5rem,1rem_+_3cqi,3rem)]` |
| `h3` 크기 | `text-4xl md:text-5xl lg:text-6xl` | `text-4xl md:text-5xl lg:text-[length:clamp(1.75rem,1.25rem_+_2.5cqi,3rem)]` |
| `h3` 줄 간격 | (text-6xl 기본값 그대로) | `lg:leading-tight` 추가 |
| `h3` 나머지 | `font-medium mb-16 break-keep text-balance` | 동일, 변경 없음 |
| 역할·기간 줄 | `text-sm md:text-base` | 동일, 변경 없음(lg에서 16px 유지) |
| 그라디언트 | `bg-linear-to-t from-black/70 from-50% to-transparent` | 동일, 변경 없음 |
| 썸네일 `Image` | `object-cover`, `sizes` 그대로 | 동일, 변경 없음 |

- `[length:...]` 힌트는 Tailwind가 임의 값을 font-size로 해석하게 하는 표기다. `_`는 공백이다(clamp 안 연산자 양옆 공백을 보장).
- 변형이 켜졌을 때 `lg:text-6xl`, `lg:p-64`가 클래스 문자열에 남지 않아야 한다(둘 다 남으면 어느 쪽이 이길지 CSS 순서에 맡기게 됨).
- 위 두 값은 `cqi`를 쓰므로 와이드 변형의 `h3`와 컨테이너는 `lg:@container`가 붙은 `Link`의 자손이어야 한다. 현재 DOM에서 둘 다 `Link` 자손이고, `preserveThumbnailText`용 `containerType: size` 래퍼는 썸네일 영역 안 형제 서브트리라 텍스트 블록의 컨테이너 해석에 끼어들지 않는다.
- `@container`가 없는데 `cqi`를 쓰면 작은 뷰포트 단위(sv*)로 대체된다(MDN). 와이드 변형은 반드시 `lg:@container`와 함께 켠다.

값의 크기(1px = 1 기준, 1rem = 16px):

| 카드 폭 | 패딩 | 제목 | 제목 줄 간격 적용 시 1줄 높이 |
| --- | --- | --- | --- |
| 491 (뷰포트 1024) | 약 30.7px | 약 32.3px | 약 40px |
| 640 (1280) | 35.2px | 36px | 45px |
| 687 (1440) | 약 36.6px | 약 37.2px | 약 46.5px |
| 967 (최대폭) | 약 45px | 약 44.2px | 약 55px |

- 홈 카드(1200폭, 제목 60px, 패딩 64px)와의 비율: 1440의 `/projects` 카드는 제목 약 5.4%(홈 5.0%), 패딩 약 5.3%(홈 5.3%)로 카드 폭에 대한 비례를 비슷하게 유지한다.
- 제목 최소 1.75rem(28px), 최대 3rem(48px): 최대/최소 비율 약 1.7로 2.5배 이하(웹 검색 기록 5의 지침).
- 제목은 항상 24px 이상이라 WCAG 큰 글자(18pt 약 24px) 기준 3:1 적용 구간이다. 역할·기간 16px은 작은 글자라 4.5:1 기준이다.

**(c) 단계식 대체안(컨테이너 방식이 문제될 때만)**: `lg:@container`를 쓰지 않고 중단점으로 대체한다. 패딩 `lg:p-32 2xl:p-48`, 제목 `lg:text-3xl 2xl:text-4xl`(둘 다 기존 토큰, 같은 방식으로 조건 분기). 카드가 연속적으로 커지지 않고 1536에서 한 번 점프하는 단점이 있어 기본안이 아니다.

### 6.3 가독성 검증 (그라디언트 유지 근거)

계산은 순백(255) 픽셀을 최악 배경으로 가정한 선형 합성이며, 이 단계에서 렌더 화면을 측정한 것은 아니다.

- 그라디언트는 바닥에서 위로 `from-black/70`이 50% 높이까지 평평하고 그 위는 위쪽 끝에서 투명이 되도록 선형으로 줄어든다.
- 순백 위 검정 70%는 약 rgb(77,77,77)이고 흰 글자 대비는 약 8.5:1(4.5:1 이상).
- 위 구간에서 요구 투명도: 순백 배경 기준 4.5:1을 만족하려면 알파 약 0.535 이상, 3:1은 약 0.416 이상.
- 이를 만족하는 최대 높이 비율: 4.5:1은 바닥에서 약 61.8%, 3:1은 약 70%까지.
- 텍스트 블록이 카드에서 차지하는 높이 비율(와이드 변형, 제목 2줄): 1024에서 약 53%, 1440에서 약 44%, 제목 1줄이면 더 작음. 모두 61.8% 안이라 그라디언트를 바꾸지 않아도 최악 조건에서 기준을 만족한다.
- 제목 3줄이 되는 긴 제목(1024, 제목 줄 간격 40px 기준 블록 약 68%)은 제목 맨 윗줄이 큰 글자 기준 3:1 한계(약 70%)에 거의 닿는다. 이 경우는 허용 범위의 가장자리이므로 T09에서 가장 긴 제목으로 1024 화면을 확인한다.
- 16:9로 카드가 낮아지면 텍스트 블록이 카드에서 차지하는 비율이 이전(675 높이에서 약 15~20%)보다 커진다. 기존 그라디언트의 평평한 구간(50%)이 이를 덮으므로 클래스 변경은 하지 않는다(변경 최소화 원칙, 기존 Framer 디자인 보존).

### 6.4 레이아웃 시프트(CLS)와 높이 안정성

- 카드 높이는 CSS `aspect-ratio`(폭 대비 16:9)에서 결정되고 이미지 로드나 폰트 교체에 의존하지 않는다. `Image`는 `fill`(`absolute inset-0`)이라 이미지 크기가 카드 크기에 영향을 주지 않는다. web.dev는 이미지에 `width`/`height`를 주거나 CSS `aspect-ratio`로 공간을 미리 확보하라고 안내한다(웹 검색 기록 2). 이 카드는 후자의 방식으로 공간이 미리 확정된다(AC-15).
- 텍스트 블록은 `justify-end` 하단 정렬이고 카드 높이가 고정이라 폰트 로드로 줄바꿈이 달라져도 카드 높이와 아래 요소 위치는 변하지 않는다. 대신 긴 제목이 위로 자라고 `overflow-hidden`이 넘친 부분을 자른다(1024, 제목 4줄 이상이면 발생 가능, 6.3 참고).
- 구현 확인 항목: `h-auto` + `aspect-ratio`인 `Link` 안의 자식 `relative z-10 h-full`(텍스트 블록)이 비율로 계산된 높이를 퍼센트로 해석하는지 확인한다. 브라우저에서 높이가 0처럼 보이거나 텍스트가 카드 밖으로 나가면, 와이드 변형에 한해 텍스트 블록 컨테이너를 `lg:absolute lg:inset-0`로 바꾼다. 이 단계에서는 실측하지 않았다.

### 6.5 이미지 비율과 크롭

- 1440에서 카드 비율은 약 1.78(687/386)로 16:9와 같다. 16:9 PC 이미지(SEMT.png 3840x2160, Candanta 신규 3840x2160)는 `object-cover` 기본 위치에서 사실상 전체가 보인다. 1차본 6절의 "좌우 약 23% 크롭, 헤드라인 앞부분 손실" 문제는 해소된다.
- 16:9가 아닌 기존 PC 이미지(예: Globber 현재 썸네일)는 비율 차이만큼 크롭된다. 비율을 이 단계에서 확인하지 못했다. T09에서 `/projects` 1440 스크린샷으로 확인하고, 이는 D3로 의도된 변경이라 AC-R2 대상이 아니다.
- 하단 그라디언트와 텍스트가 이미지 하단 약 40~50%를 덮는 점은 홈 카드와 같은 구조다.

### 6.6 2열 레이아웃(카드와 요약) 정렬

- 컬럼 구성(7/1/4), `items-start`, 오른쪽 `sticky top-128` 요약 래퍼, `min-h-project-info`(200px)는 변경하지 않는다. 카드가 낮아져도 행 높이는 `max(카드 높이, 요약 칸 높이)`가 된다.
- 위쪽 정렬: 카드 윗면과 요약 첫 줄 위치가 같은 기준선(`items-start`)에서 시작한다. 요약 `text-h3`는 줄 간격 1.75라 글자 윗면이 카드 윗면보다 반 줄 간격(1440에서 약 12px) 아래에 놓인다. 이는 현재와 같은 상태이고 이번 변경으로 달라지지 않는다. 보정은 하지 않는다.
- 요약이 카드보다 긴 경우: 1024에서 요약 칸은 약 267px 폭, 글자 약 31px이라 요약이 길면 행이 카드(276)보다 높아질 수 있다. 이때 카드는 `top-160`에 스티키되어 행 안에서 따라오고, 요약 래퍼도 `top-128`에 스티키되어 기존과 같은 스크롤 동작이다. T09에서 가장 긴 요약으로 1024와 1280을 확인한다.
- 일관된 카드 높이: 모든 카드가 같은 비율이라 행마다 카드 높이가 폭에 비례해 같다(카드 크기가 콘텐츠 길이에 따라 달라지지 않음).

### 6.7 AC-R2 예외 (픽셀 동일 기준)

AC-R2의 픽셀 동일 기준에서 D3로 의도 변경된 부분은 제외한다. 구체적으로:

- 제외(변경이 정상): `/projects` 페이지의 뷰포트 1024 이상에서 카드 크기(높이 75vh에서 16:9), 그 안의 이미지 크롭, 제목 크기와 줄 간격, 텍스트 블록 패딩, 이에 따른 행 높이와 아래 카드·요약 칸의 위치. 썸네일이 없는 프로젝트(AC-R1)의 `/projects` lg 이상 카드도 같은 사유로 제외한다.
- 유지(픽셀 동일 필요): 홈 카드 전 구간(375, 768, 1024, 1440), `/projects`의 375, 768, 1023, 크롭 위치(lg 미만), 그라디언트 오버레이 값, 호버 확대, 포커스 링, 역할·기간 줄 스타일.
- 검증 방법: T09는 `/projects` 1024 이상 구간은 6절 명세값(비율 16:9, 6.2 클래스, 6.2 크기표)과 비교하고, 그 외 구간은 변경 전 스크린샷과 픽셀 비교한다.

## 7. admin 폼 명세 (A7, F6)

### 7.1 배치

`project-form.tsx`의 기존 단일 `ThumbnailField` 자리를 "썸네일" 영역으로 교체한다. 위치는 "프로젝트 링크" 다음, "기술 스택" 앞(현재 위치 그대로).

```
썸네일 (fieldset, 큰 legend)
  안내문: 순서가 곧 전환 순서입니다. 2장 이상이면 공개 화면에서 4초마다 전환됩니다.
  [기본 썸네일 목록]  (fieldset, legend "기본 썸네일")
    힌트: PC 화면에 표시되며, 모바일 썸네일이 없으면 모바일에서도 사용합니다. 최대 10장.
    행 1: 미리보기 + 파일 입력/상태 | 위로 | 아래로 | 삭제
    행 2: ...
    [기본 썸네일 추가]   n/10
    오류 메시지
  [모바일 썸네일 목록]  (fieldset, legend "모바일 썸네일")
    힌트: 모바일 화면(768px 미만)에 표시됩니다. 비워두면 기본 썸네일을 사용합니다. 최대 10장.
    행들, [모바일 썸네일 추가]   n/10, 오류 메시지
```

### 7.2 컴포넌트와 재사용

| 대상 | 재사용/신규 | 설명 |
| --- | --- | --- |
| 목록 틀 | 기존 `src/components/admin/list-editor.tsx`(`ListEditor`) | 추가·삭제·위/아래 이동, 포커스 이동, `aria-live` 안내가 이미 있음. 개수 상한 `LIST_MAX = 50` 상수가 고정이라 `max`를 props로 받게 해야 함(기본 50 유지, 이번에 10 전달). 삭제 뒤 포커스 이동은 `input, textarea`를 찾으므로 썸네일 행의 파일 입력에도 동작하는지 확인 필요 |
| 행 내용 | 기존 `thumbnail-field.tsx`(`ThumbnailField`) | 업로드 검증(PNG/JPG/WebP, 4MB, 빈 파일), 미리보기, 오류·진행 상태 재사용. 아래 수정 필요 |
| 버튼 | 기존 `AdminButton`(`icon`, `danger`, 기본) | 신규 버튼 컴포넌트 없음 |
| 드롭다운·모달·툴팁 등 | 없음 | `src/components/common/`에 해당 컴포넌트 없고, 이번 명세에 필요한 인터랙티브 primitive도 없음. Radix 불필요 |

`ThumbnailField`가 목록 행에서 쓰이기 위해 필요한 변화(UX 관점, 구현 방식은 개발자 영역):

- 입력 `id`, 힌트·오류 id가 고정 문자열(`project-thumbnail`)이라 행마다 유일해야 한다.
- 라벨 문구 "썸네일 파일"이 행마다 중복되므로 행 단위 접근 가능한 이름을 받아야 한다. 예: "기본 썸네일 2 파일", "모바일 썸네일 1 파일".
- 행 안의 "썸네일 제거" 버튼은 행 삭제와 중복이므로 목록 행에서는 숨긴다("이미지 교체"는 유지).
- 모바일 목록의 미리보기는 세로형 이미지가 기대되므로 현재 `h-192 w-full max-w-xs`(가로형) 대신 세로 비율 칸(예: 높이 192px에 폭 약 108px)으로 보여 준다. 기본 목록은 현재 크기 그대로.
- 안내 문구 "업로드와 제거는 프로젝트 저장 후 반영됩니다."는 목록 영역 안내문에 한 번만 둔다(행마다 반복하지 않음).

### 7.3 행 상태

| 상태 | 표시 |
| --- | --- |
| 빈 행(방금 추가) | 파일 입력만 보임(현재 빈 값 상태와 같음). 위/아래/삭제는 사용 가능 |
| 업로드 중 | "썸네일 업로드 중..." `role="status"`(현재 문구 유지) |
| 업로드 완료 | 미리보기와 "이미지 교체" |
| 업로드 오류 | 행 안에 `role="alert"` 오류(현재 동작) |
| 저장 오류(서버/스키마) | 해당 목록 fieldset 아래 오류 한 줄(5개 이하 행 단위 오류는 행 안) |

### 7.4 목록 규칙

- 최대 10장. 10장이면 "추가" 버튼 비활성화, 옆에 "최대 10장" 표시. 항상 "n/10" 개수를 힌트 옆에 노출한다.
- 위/아래 버튼: 첫 행은 위로, 마지막 행은 아래로 비활성화. 접근 가능한 이름은 "{항목명} {번호} 위로 이동"(`ListEditor` 형식 그대로, 항목명은 "기본 썸네일"/"모바일 썸네일").
- 이동·삭제 뒤 `aria-live="polite"`로 위치 안내(`ListEditor` 기존 문구 재사용).
- 업로드 진행 중(어느 행이든)에는 같은 폼의 두 목록 모두에서 추가·이동·삭제와 저장을 비활성화한다. 이유: 행이 이동하거나 사라지면 업로드 결과가 엉뚱한 행에 들어간다. 기존 "저장 전 업로드 완료" 규칙(AC-22)을 목록 전체로 확장하며, 동시 업로드 수를 세어 하나라도 있으면 막는다.
- 빈 행으로 저장하려 하면 필드 오류: "이미지를 올리거나 빈 항목을 삭제하세요."(AC-20).
- 같은 목록 안에서 중복 URL이면 필드 오류: "같은 이미지가 중복되었습니다."(AC-20). PC와 모바일 목록 사이 동일 URL(E-i)은 허용(저장 허용, 공개 화면에서 목록이 같으면 세트가 합쳐짐은 3.2).
- 기본 목록이 비고 모바일 목록만 있으면 저장 거부(확정 A4): 기본 목록 오류 "모바일 썸네일만 등록할 수 없습니다. 기본 썸네일을 추가하세요."
- 두 목록 모두 비어 있는 상태는 정상(썸네일 없음).

### 7.5 저장·변경 감지

- 수정 화면에서 썸네일을 건드리지 않으면 현재 `savedThumbnail` 비교와 같은 의미로 썸네일을 서버에 보내지 않고 레거시 검증 우회 경로를 쓴다(AC-21). 두 목록 각각에 대해 "저장 당시 값과 순서·내용이 같으면 변경 없음"으로 판단한다.
- 한 목록만 바꿨다면 바뀐 목록만 보내고 건드리지 않은 목록은 생략한다(api-spec 3.3절). 디자인 요구는 건드리지 않은 목록 값이 변하지 않는 것.
- 제거된 이미지의 Blob 정리는 기존 단일 썸네일과 같은 방식(확정 E2).

### 7.6 반응형·접근성 (admin)

- `md` 미만: 행이 세로로 쌓이고 컨트롤은 아래에 줄바꿈(`ListEditor` 현재 동작). `md` 이상: 행 내용과 컨트롤이 가로 배치.
- 모든 버튼 최소 높이 44px(`AdminButton` 기본값), 포커스 아웃라인 기본 유지.
- 두 목록은 각각 `fieldset`+`legend`로 그룹화해 스크린리더에서 "기본 썸네일"/"모바일 썸네일" 맥락이 읽히게 한다.
- 오류 메시지 요소는 `data-error-focus`로 제출 실패 시 첫 오류에 포커스가 가는 기존 패턴을 따른다.

## 8. 파일·네이밍 제안

- 공개 전환 컴포넌트: `src/components/common/project-card-thumbnails.tsx`(클라이언트, kebab-case). `ProjectCard`는 `project-card.tsx` 유지.
- 상수: `src/constants/` 안 한 파일(간격 4000ms, 페이드 600ms).
- admin: 별도 목록 컴포넌트가 필요하면 `src/components/admin/thumbnail-list-field.tsx`(목록 하나 담당, `ListEditor`+`ThumbnailField` 조합)를 쓰고, 기본/모바일 두 번 사용한다. 실제 파일 배치는 T05가 `project-structure.md`와 knip 규칙에 맞게 결정.
- 디자인 토큰: 새 색 없음. 흑백 팔레트와 기존 토큰만 사용. 6.2절의 `clamp(...)` 임의 값은 카드 폭에 비례하는 연속값이라 토큰으로 표현할 수 없어 `tailwind.md` 4번(1회성 임의 값 허용)에 해당한다. 같은 값을 다른 곳에서 쓰게 되면 `@theme` 토큰화를 검토한다. 모바일 미리보기 폭 같은 px 값이 필요하면 `tailwind.md` 규칙대로 px 환산 클래스를 쓴다.

## 9. 사용자/PM 확인이 필요한 항목

1. (해소) 1차본의 `/projects` 데스크톱 SEMT PC 이미지 크롭 판단 요청은 D3(카드 16:9)로 해소됐다. 남는 확인은 16:9가 아닌 기존 이미지(예: Globber)의 `/projects` lg 이상 크롭이 허용 가능한지 T09 스크린샷에서 보는 것뿐이다(6.5절). 이는 D3로 의도된 변경이라 별도 결정 요청은 아니다.
2. 경로 C(PC와 모바일 목록이 다름)의 첫 카드를 lazy로 두는 LCP 트레이드오프(3.5). 이 단계에서는 lazy로 확정 제안, T09에서 실측 후 `<picture>` 대안 전환 여부 판단.
3. 목록 행의 모바일 미리보기 비율은 세로 칸(약 108x192)을 제안. 다른 크기를 원하면 알려 달라.
4. 알림: D4 데이터 반영 전에는 Candanta가 단일 세트(정사각 가운데 크롭)라 `/projects` lg 이상 16:9 카드에서 좌우 약 150px에 배경색이 보인다(3.3절). 코드 배포가 D4 데이터 반영보다 먼저 나가는 순서라면 잠깐 보이는 모습이다. 배포 순서를 바꿀 필요가 있으면 알려 달라.
5. 제목·패딩을 카드 폭 비례(컨테이너 단위 `clamp`)로 한 결정(6.2절 기본안)이 괜찮은지. 단계식 대체안이 6.2(c)에 있다. 기본안으로 진행하되 T05에서 `lg:@container` 동작이 확인되지 않으면 대체안으로 내려간다.

D3 지시에 따라 변경된 디자인(작아진 16:9 카드, 이미지 위 텍스트, 2열 정렬)에 맞는 근거를 검색·열람한 기록이다. "채택"은 6절 결정의 근거로 쓴 것, "참고"는 열람했으나 결정 근거로 쓰지 않은 것이다.

### 11.3 근거의 한계

- 2열 레이아웃(카드와 요약) 정렬은 1차 출처로 뒷받침하지 못했다. 6.6절 결정(기존 컬럼 구성 유지, `items-start` 위쪽 정렬 유지, 보정 없음)은 기존 Framer 디자인 보존 원칙과 현 코드에 근거한 것이며 외부 best practice 근거가 아니다.
- 제목·패딩 비율(6.2절)은 홈 카드의 비율을 기준으로 한 설계 판단이며, 외부 문서가 특정 비율을 제시한 것은 아니다. 근거가 되는 외부 지침은 `rem` 기본값 유지와 최대/최소 2.5배 이하(5), 컨테이너 단위 사용법(3, 3a)이다.
- 6.3절 대비 수치는 이 문서에서 직접 계산한 값이며 렌더 측정이 아니다. WCAG 기준값(1)과 합성 공식으로만 도출했다.
