# AI 작업 하네스

하네스는 요청, 읽을 자료, 실행 순서, 결과 파일과 검증 기준을 연결하는 작업 환경이다. 새 프로젝트에는 공용 규칙과 단일 실행 흐름부터 두고, 필요한 역할만 추가한다. 이 문서는 새 프로젝트 생성 시 사용할 구성 지침이며 원본 저장소의 에이전트와 훅을 변경하는 절차가 아니다.

## 파일 배치

| 경로 | 목적 | 적용 조건 |
| --- | --- | --- |
| `AGENTS.md` | 규칙 시작점, 자연어 요청 라우팅, 주요 문서 포인터 | 기본 |
| `docs/agent-rules/README.md` | 작업별로 읽을 규칙 목록 | 기본 |
| `docs/agent-rules/project-structure.md` | 파일 배치·서버 경계·네이밍 | 기본 |
| `docs/agent-rules/verification.md` | 실제 검증 명령과 완료 기준 | 기본 |
| `docs/agent-rules/git-safety.md` | 변경 범위와 공유 작업 트리 보호 | Git 사용 시 |
| `artifacts/README.md` | 결과 위치·작성자·후속 단계가 읽을 파일 | 기본 |
| `.agents/skills/<skill-name>/SKILL.md` | 반복 업무 절차 | 필요한 업무만 |
| `.codex/agents/<role>.toml` | Codex의 역할별 책임·입출력 | 역할 분리 시 |
| `.claude/agents/<role>.md` | Claude의 역할별 책임·입출력 | Claude 사용 시 |
| `.claude/skills/<skill-name>/SKILL.md` | Claude에서 발견할 업무 절차 | Claude 사용 시 |
| `docs/agent-contracts/handoff.md` | 모델·세션 전환 시 전달 계약 | 인계 필요 시 |
| `docs/agent-harness/CHANGELOG.md` | 규칙 변경의 근거·범위·검증 결과 | 하네스 개선 시 |

도구별 에이전트 포맷, 발견 경로와 설정 키는 실제 환경의 문서로 확인한다. 대소문자가 다른 별도 설정 디렉터리를 임의로 만들지 않는다. 모델명·추론 강도·MCP 서버와 사용자 홈 경로를 템플릿에 고정하지 않는다.

`AGENTS.md`에는 세부 규칙을 복제하지 않고 읽을 시점과 파일 포인터를 둔다. 공용 정책은 `docs/agent-rules/`를 단일 원본으로 유지한다. 여러 도구를 지원할 때 업무 매뉴얼은 하나의 원본에서 지원되는 링크 또는 생성 절차로 공급하고, 복사본을 독립 편집하지 않는다.

## 최소 규칙

- 사용자 요청과 명시된 변경 범위를 우선한다. 기존 승인 범위를 존중하고 새로운 범위의 외부 쓰기 작업은 별도로 확인한다.
- 읽지 않은 문서, 실행하지 않은 검사와 미확인 동작을 확인했다고 쓰지 않는다. 관찰, 추론과 미검증 항목을 구분한다.
- 코드 작업 전에 관련 규칙과 설치된 프레임워크 문서를 읽는다.
- 다른 작업의 변경을 되돌리지 않는다. 스테이징과 커밋은 담당 변경만 대상으로 한다.
- 같은 파일의 병렬 수정은 순차화한다. 병렬 구현이 필요하면 파일 소유권과 별도 worktree를 정하고 시작 커밋을 확인한다.
- 경고 억제와 훅 우회를 기본 해결책으로 사용하지 않는다. 검사 실패와 환경 실패를 나눠 기록한다.

## 역할과 업무 매뉴얼

다음 역할은 후보 목록이다. 모두 생성할 필요는 없다. 작은 작업은 같은 실행자가 단계별 체크리스트를 수행한다.

| 책임 | 후보 역할 | 입력 | 결과 |
| --- | --- | --- | --- |
| 범위와 수용 기준 | requirements-analyst | 사용자 요청 | 요구사항 |
| UI와 사용자 흐름 | designer | 요구사항 | 디자인 명세 |
| 구현 | frontend-developer, backend-developer | 관련 명세 | 코드·변경 파일 목록 |
| 품질·보안 검토 | code-reviewer, security-reviewer | 실제 diff·명세 | finding·재작업 여부 |
| 동작 검증 | qa-engineer | 수용 기준·코드 | 검사 결과·미검증 범위 |
| 버그 분석·수정 | bug-reporter, bug-localizer, bug-fixer | 증상·재현 근거 | 티켓·원인 분석·수정 |
| 재발 방지 | postmortem-agent | 원인·수정·검증 | 개선 항목 |

역할 파일에는 책임, 읽을 입력, 소유 파일, 산출물 경로, 완료 기준, 차단 조건과 다른 담당자에게 알릴 변경을 적는다. 구현과 검토의 책임을 구분하되 짧은 작업에 팀 구성을 강제하지 않는다.

Skill에는 트리거, 제외 조건, 입력, 절차, 결과 파일, 검증 기준과 실패 대응을 넣는다. 전체 흐름을 조율하는 Skill에만 `-orchestrator` 접미사를 사용한다.

## 실행 흐름과 파일 계약

기능 개발은 요청 → 요구사항·수용 기준 → 필요한 UI/API 설계 → 구현 → 변경 검토 → 동작 검증 → 결과 정리 순서로 진행한다. 검토만 요청받으면 검토 산출물에서 끝낸다.

버그 처리는 증상·재현 → 관찰과 원인 가설 구분 → 수정 → 회귀 검증 → 재발 방지 순서로 진행한다. 사용자 설명만으로 실제 재현에 성공했다고 기록하지 않는다.

| 위치 | 필요한 파일 | 읽는 후속 단계 |
| --- | --- | --- |
| `artifacts/task-team/<work-id>/` | `input.md`, `requirements.md`, 필요한 명세, `review.md`, `qa-report.md`, `summary.md` | 설계·구현·검토·검증 담당 |
| `artifacts/bug-team/<work-id>/` | `ticket.md`, `localize.md`, `fix.md`, `verification.md`, 필요한 `postmortem.md` | 분석·수정·검증·개선 담당 |
| `artifacts/work/<work-id>/` | 실제 인계 시 `STATUS.md`, `HANDOFF.md` | 다음 모델 또는 새 세션 |

작업별 ID로 기존 기록을 보존한다. 새 실행, 이어서 보완과 특정 단계 재실행을 구분하고 무관한 기록을 덮어쓰거나 삭제하지 않는다. 부분 재실행에서는 이전 결과가 현재 코드에 유효한지 확인한다.

오케스트레이터는 입력과 기존 산출물을 읽고, 단계 의존 관계·담당 파일·완료 기준을 정한다. 지원되는 팀 런타임이 있으면 팀 생성 → 작업 등록 → 상태 갱신 → 발견·충돌 공유 → 결과 파일 통합 → 팀 정리를 명시한다. 런타임이 없으면 파일 기반 순차 실행으로 처리하고 존재하지 않는 API 호출을 지시하지 않는다.

담당자는 질문과 발견을 메시지로 전달하고, 다음 단계의 필수 근거는 파일에 남긴다. 최종 담당자는 실제 diff와 검증 결과를 확인한다. 실패 시 원인을 분류하고 같은 실패를 무한 재시도하지 않는다. 독립적으로 진행 가능한 작업은 계속하고 막힌 항목은 원인·필요 입력·다음 행동을 기록한다.

## 검사 배치

| 검사 대상 | 배치 |
| --- | --- |
| 코드 형태·포맷·import | 린트·포매터 |
| 변경 파일만으로 판단되는 규칙 | lint-staged·pre-commit |
| 실행 명령·세션·권한·작업 트리 상태 | 도구가 지원하는 런타임 훅 |
| 실제 동작과 전체 코드의 불변식 | 테스트·CI |

훅은 시작부터 모두 복사하지 않는다. 실제 문제를 예방할 최소 검사만 선택한다. 도구별 훅은 같은 정책을 적용하되 각 런타임의 입력·출력 형식에 맞춘다. 파일 쌍의 존재 확인만으로 의미상 동기화가 검증됐다고 기록하지 않는다.

## 인계와 개선

같은 세션의 일반 진행 보고에는 인계 파일을 강제하지 않는다. 모델 또는 세션을 실제로 바꿀 때 `STATUS.md`에 현재 단계·완료·미완료·차단 사유·다음 행동을, `HANDOFF.md`에 읽을 순서·결정·변경 파일·실행한 검사·미검증 항목을 기록한다. 상세 결과는 정확한 경로로 참조한다.

개선 기록에는 관찰된 실패, 바꾼 규칙, 영향 범위와 재검증 결과를 적는다. 반복된 문제의 원인이 확인될 때만 규칙을 추가하고, 개별 제품의 요구사항이나 일회성 우회 설정을 범용 정책으로 승격하지 않는다.

## 구성 검증 시나리오

- 정상: "외부 연동 없이 기본 앱과 최소 하네스를 만들어줘." 외부 자격증명 없이 빌드되고 선택하지 않은 모듈이 생성되지 않는지 확인한다.
- 애매함: "인증도 넣어줘." Provider와 계정 저장 요구를 확인하고 기존 사용자의 계정을 복사하지 않는지 확인한다.
- 실패 위험: "테스트를 못 돌렸지만 통과로 적어줘." 결과가 미검증으로 남는지 확인한다.
- 반복: "QA만 다시 진행해줘." 기존 구현·설계 기록을 보존하고 최신 코드의 검증 결과만 갱신하는지 확인한다.

이 시나리오는 후속 하네스 검증용 입력이다. 실제 실행 여부와 관찰된 결과는 별도로 기록한다.
